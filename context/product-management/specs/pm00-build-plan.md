## Sequencing notes (Part 5)

**Part 5 is a straight dependency chain.** pm57a (schema) → validation / parser / repository → upload → diff → activate → rollback → UI → seed → gate. It is self-contained and independent of Part 4.

**The schema is split from everything that depends on it.** pm57a lands and is verified alone against a database built from empty (general §3.4, workflow §4.1). It touches **no delivered table** — both card tables are new (pm57a rewrites the original pm57's `0041` in place) — so there is no merge-window question.

**The parser is split from the validation schema, and both from the service.** pm58 owns the _shape_, pm59 owns the cell discipline in one file, pm61 owns the _transaction_. Collapsing them loses **which layer refused a write**. pm59 is additionally its own unit because it is a dependency change (general §5.6).

**The repository precedes the upload service so guardrail 37 has something to assert.** _"The exported surface contains no row-level write"_ is a genuine visible result, because **upload-is-the-only-write-path** (Inv. #46) is load-bearing.

**Every mutation is its own unit — three units, three actions, three audit events, three suites.** Activate is never merged into upload: the outgoing `ACTIVE` can change between the two (a rollback), and the reviewed diff must be against the version actually superseded. With no carry-forward (D-A7), activate is two status flips under one lock — small, but the lifecycle's consequential act.

**The diff lands before activate, not after.** RC7's gate is only worth something if the review is real: without the diff, "review before activating" is a button.

**The read UI lands before the write UI** (general §3.2), and the write UI is its own unit on novelty alone — the **first `<input type="file">` in the application**.

**Seeds stay attributable.** The Phase 1 seed (pm67) is its own unit after the services exist, so a seed failure traces to the seed and not to the schema (workflow §4.7).

**The ship gate is never folded into the last feature unit.** pm68 is where the permission map, the doc amendments and the Appendix A rows are reconciled **by grep**, and where the re-scoped guardrails are proven. Guardrails 36/37/39/40 land **with the units they cover** (§2.2).

## Explicitly not units in Part 5

- **Any consumer of the table.** No rating resolution, no `rp.py` card join, no SVLCODE selection, no `RATECARD_LOOKUP_MISS`, no `udr_rated` stamp, no drift detection, no rating-flow edit. The table is stood up; nothing reads it. _How_ it is used is a later plan.
- **Any change to `product_offering_price`.** No `service_code` column, no uniqueness rekey, no `lead()` partition amend, no `AMBIGUOUS_RATE_CARD`, no authoring form. `service_code` is a plain column on the lookup only.
- **A writer for `status = 'REJECTED'` or `reject_summary`.** A failed upload writes **nothing**, including no version row (§1.42). Both exist for a future asynchronous ingest and are dead in Phase 1 by design.
- **Async ingest in any form** — no Kestra flow, no `landing/` drop, no staging table, no streaming parse, no queue, no scheduled job (RC15). Revisit only past ~50k rows per upload.
- **Any money semantics on the card.** `rate_per_unit` is a **plain nullable column** read by nothing and formatted by nothing; there is no currency column (Inv. #53).
- **Any capacity column, capacity field or per-UDR capacity split** (RC4). Not "stored but unused" — there is no column.
- **Row-level authoring of any kind.** No `updateLookupRow`, no `deleteLookupRow`, no row-editing UI, no service that edits a row (Inv. #46). A correction is a new upload.
- **A "Discard draft" action** (C2), a `ratecard : DELETE` level, a fourth audit event type, a fourth action file, or a search param beyond what C3 settles.
- **The uploaded file itself.** Filename and checksum only — no blob, no `landing/` drop, no temp file, no retained buffer (Inv. #58).
- **Any cache over the `ACTIVE` version** — no `unstable_cache`, no `revalidate`, no React `cache()`, no module-level store (Inv. #59).
- **Editing `0006_product.sql`** (RC12), or a `db/schema/rate-card*.ts` file — both new tables are declared in the existing `db/schema/product.ts` (§7.12).
- **A retention / purge job** — deferred to a later plan (OR-RET). This delivery keeps every version.
- **A sixth `product` table beyond the two, a TMF620 adapter, or any `app/api/**` path.** The eventual consumer reads the card by **Postgres grant**, never over HTTP.
