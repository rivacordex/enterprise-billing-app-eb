## pm63 (current unit) — full detail

**pm63 (Activate): IMPLEMENTED, unit-tested, NOT yet run against a live DB this session (2026-09-28, same session as pm62).** Part 5. Boundary per `specs/pm63-activate.md`: `services/product/ratecard/activate-version.ts` (new), `actions/product/activate-ratecard-version.action.ts` (new — `PRODUCT_ACTION_FILES` +1, second of three, guardrail updated same commit), the `RATECARD_VERSION_ACTIVATED` audit type and its full three-part ripple, guardrails 36 and 39 (service arm + the 4×-looped race), and this unit's live-DB/concurrency tests. **D1's TOCTOU-safe lock needed a repository addition pm63's own boundary line doesn't list, added and flagged rather than worked around.** D1 requires the target `DRAFT` locked `FOR UPDATE` in addition to the outgoing `ACTIVE` (pm60's existing `findActiveForUpdate`) — but no existing pm60 export locks a specific version **by id**, and the DRAFT's own `card_name` (needed to look up its ACTIVE sibling) is only known once that row is read. Added `findVersionForUpdate(tx, versionId)` to `db/repositories/ratecard.ts` — a locked-by-id read, the same primary key `deleteDraftVersion` already locks internally, so a concurrent re-upload's replace-open-draft delete (pm61 D12) and an activation of that same draft serialize on Postgres's row lock rather than interleaving. Read-only (matches the `get`/`find` naming pattern the guardrail-37 exported-surface test already excludes from its mutation regex), so `tests/db/product-repository-exports.test.ts` needed no change.

**Activation flow, in order:** (1) lock the target DRAFT by id (`findVersionForUpdate`), re-read its status — `VERSION_NOT_FOUND` / `NOT_DRAFT` typed refusals, never a throw; (2) lock the card's current `ACTIVE` (if any) via pm60's `findActiveForUpdate` — `null` is the ordinary first-ever-activation case, not an error; (3) compute the diff **inside this transaction, on this same `tx`**, by calling pm62's `diffAgainstActive(tx, cardName, versionId)` directly (no client-supplied counts ever reach the audit payload); (4) two `setVersionStatus` calls — promote the target, demote the outgoing (when one exists) — no lookup-row write anywhere in the file; (5) exactly one `RATECARD_VERSION_ACTIVATED` audit event, same transaction, `beforeData: { supersededVersionId }` / `afterData: { cardName, added, changed, removed }`.

**A second `ACTIVE` is refused twice, and the two mechanisms are provably distinct:** the service's own `NOT_DRAFT` typed check (proven first, via re-activating an already-`ACTIVE` version) and, independently, the `ratecard_version_one_active_per_card` partial unique index against a direct SQL insert that bypasses the service entirely (guardrail 39, service arm — the index arm landed at pm57a). **Concurrency proven, not assumed** (this module's standing lesson, pm14/pm15/pm16/pm20's own precedent): two concurrent activations of the same card's single open DRAFT, looped 4×, serialize on that DRAFT's row lock — the loser's lock wait ends with the draft already `ACTIVE` (the winner committed first), so it re-reads `NOT_DRAFT` rather than double-activating. Exactly one `ACTIVE` results every iteration. (D1's own prose says "two different drafts of one card" — read literally that is impossible under pm57a's one-draft-per-card partial index; the concrete, testable scenario — confirmed against `pm00-build-plan.md`'s pm63 row, which says only "two concurrent activations for one card" — is two racers targeting the one draft that exists, which is what the test suite proves.)

**Audit-category decision, recorded rather than defaulted:** `RATECARD_VERSION_ACTIVATED` is categorized `Change`, not `Additive` — unlike `PRODUCT_OFFERING_ACTIVATED` (which is `Additive`, paired with a separate `PRODUCT_OFFERING_SUPERSEDED` `Removal` event for the demoted sibling). pm63-spec D5 deliberately writes **one** event for both movements, so it reads as a bundled status transition (matching `PRODUCT_OFFERING_SUBMITTED_FOR_TESTING` / `BILL_RUN_TRIGGERED`'s classification), not as a new entity being created. Full ripple landed in this change set: `types/audit.ts` (`AUDIT_EVENT_TYPES`), `types/audit-log.ts` (`AUDIT_EVENT_CATEGORY_MAP`), and `tests/components/audit-log-filters.test.tsx` (the `RATECARD_VERSION_ACTIVATED` assertion + the option count bumped 79→80 — the count `tsc` does not catch, per `[[audit-event-type-addition-ripple]]`).

1. `tests/guardrails/product-module-boundaries.test.ts`'s "no product read path imports the audit-log write path" was already red on `dev1` because pm61's `upload-version.ts` (a legitimate write service that writes one audit event per upload) was never added to the `PRODUCT_WRITE_SERVICE_FILES` allow-list that excludes write services from this read-only-path check. `activate-version.ts` is the same shape and would have been a second offender. The same test file's "0041 (rewritten) + db/schema/product.ts freeze the current rate-card schema" asserted "0041 is the ONLY rate-card migration" — true only through pm60, stale since pm61 legitimately added `0043_ratecard_permission.sql` (G-RC3's PERMISSIONS row, always intended to ship in its own follow-up migration per pm57a's I6 split). ## Recurring patterns (apply across units — not repeated per-unit below)

- **Permission-name ripple:** adding a name to `PERMISSION_NAMES` forces that key into every hardcoded `EffectivePermissionMap` object-literal fixture across ~25+ test files (`tsc`-caught for object literals, but a few hardcoded array-length assertions are not). See `[[permission-name-addition-ripple]]`.
- **Cross-schema integration-test ripple:** every pre-existing `tests/**/*.integration.test.ts` doing a fresh `DROP SCHEMA … CASCADE` + migrate cycle needs a `DROP SCHEMA IF EXISTS "<newschema>" CASCADE` added first — otherwise the next file's migration fails with "schema already exists." See `[[new-pgschema-integration-test-ripple]]`.
- **Audit event-type ripple (every write unit):** each new `AUDIT_EVENT_TYPES` entry needs (1) an `AUDIT_EVENT_CATEGORY_MAP` entry in `types/audit-log.ts` (`tsc`-caught) and (2) a bumped event-type count + optgroup assertion in `tests/components/audit-log-filters.test.tsx` (**not** `tsc`-caught). See `[[audit-event-type-addition-ripple]]`.
- **Repository mutation allow-lists:** the `*-repository-exports` and `*-module-boundaries` guardrails carry a per-write-unit allow-list entry — expected, not a surprise; add the entry in the same commit as the write.
- **New-route ripple:** `tests/app/route-manifest.test.ts`'s `ROUTE_MANIFEST` is a strict set-equality check against every real `app/**/page.tsx` — a new page 404-fails that test until its literal URL is added to the array.
- **Region/seam discipline:** a shell unit builds placeholder frames with `{/* pmXX */}` seam comments; each follow-up unit fills exactly one seam, leaving the others byte-unchanged (pm05→pm08, pm18→pm23, pm27→pm29/pm31/pm33).
- **`db → validation` ESLint boundary:** any `db/**` or `types/**` file that embeds a Zod-owned shape needs `"validation"` added to its allowed-import targets in `eslint.config.mjs` (first hit in pm02/pm03 — a forced companion change, not scope creep).

## Permanent lessons (from post-ship fixes — do not re-learn)

- **Grant-per-schema on deploy:** a deployed instance 500'd (`42501: permission denied for schema product`) because `bootstrap-db-roles.sql` only granted on `core` (pm09). **Any new schema must add its own grant/revoke block (incl. sequence grants) in the same change that adds its migration, and the file must be re-run**, or this recurs. See `[[db-role-bootstrap-per-schema]]`.
- **TOCTOU-safe status reads:** a status-gated branch/lifecycle decision must read its target's status on the transaction (`tx`, `FOR UPDATE`), immediately before the write — never from a pre-transaction `db` snapshot. This exact bug was found and fixed independently in pm14, pm15, pm16, and pm20; treat a pre-transaction status read as a review-blocking defect on sight (code-standards §1 rule 13).
- **Concurrency is proven, not assumed:** single-active-per-family (pm16), approve-vs-approve / approve-vs-reject (pm30), and suspend-vs-terminate (pm32) are each verified by live-DB races looped 4×. `inventory_status_history` "latest" ordering is by the sequence id, not `created_at` (fixed at transaction start, can invert under lock contention — pm32 fix). Concurrent same-family branches are serialized by `pg_advisory_xact_lock(hashtext(rootId))` in `resolveNextVersion` (pm16 fix).
