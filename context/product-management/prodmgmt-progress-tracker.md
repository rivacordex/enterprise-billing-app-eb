**pm64 (Rollback): IMPLEMENTED, unit-tested (DB-free) AND verified live-DB against the disposable test stack (2026-09-30) — full rate-card integration project green (see the 0042 note below).** Part 5, the third and last rate-card mutation. **Rollback is the same shape as activation (D2), computed in the other direction (D4).** `rollbackRatecardVersion(versionId, actorId)` in one transaction: (1) lock the target version by id (`findVersionForUpdate`, pm60/pm63's reused locked read), re-read status — `VERSION_NOT_FOUND` / `NOT_SUPERSEDED` typed refusals, never a throw; (2) lock the card's current `ACTIVE` (`findActiveForUpdate`) — `null` is the ordinary "no current ACTIVE" case (I4.9), not an error; (3) compute the diff **inside this transaction on this same `tx`** via pm62's `diffAgainstActive(tx, cardName, targetVersionId)` — passing the **target's** id makes the target the "new" side, so the counts are automatically "target against current ACTIVE" (D4, pm62 D6, no modification needed); (4) two `setVersionStatus` calls — **demote the outgoing `ACTIVE` first (when one exists), then promote the target to `ACTIVE`** (demote-first so the non-deferrable one-ACTIVE-per-card index never transiently sees two — see the 0042 note below) — **no lookup-row write anywhere** in the file; (5) exactly one `RATECARD_VERSION_ROLLED_BACK` audit event, same transaction, `beforeData: { supersededVersionId }` / `afterData: { cardName, added, changed, removed }`.

**Lineage is the one asymmetry with activation (D3), and is implemented literally.** The outgoing (demoted) version gains `superseded_by_version_id = <target>`; the target's OWN `superseded_by_version_id` (which pointed at the version that originally replaced it) is **cleared to null** — because it is no longer superseded, and leaving a stale pointer on a live version would make the version list render a lie (`VersionStatusProvenance` already distinguishes `undefined` = leave / `null` = clear, so no repository change was needed). The target's `activated_by`/`activated_at` are **re-stamped to this rollback** — those columns record when a version is *currently* active, and the original activation survives only in the audit trail (lineage is a statement about the present; the log is the log, D3).

**No `INSERT … SELECT`, and that is the headline (D1).** A superseded version's rows are already exactly its uploaded file (RV3, Inv. #46), so restoring it needs no reconstruction — flipping two statuses puts the card back byte-for-byte. The live-DB suite's headline assertion (I4.2) is that both versions' rows are byte-identical before and after; I4.3 that neither row count changes; I4.10 the "undo-the-undo" (roll back to v1, then roll back to the now-superseded v2 — restores exactly, both directions byte-clean). **Honest consequence recorded (D2, `pm00-build-plan.md` Part 5 hand-off register):** rolling back *loses* the keys the demoted version added and the target never had — that is what rolling back means; the way to keep them is a corrected upload, not a merge.

**A second `ACTIVE` is refused twice, and the race that matters is activate-vs-rollback (D5).** The service's own `NOT_SUPERSEDED` check (proven by rolling back an already-`ACTIVE` version, I4.7) and, independently, the `ratecard_version_one_active_per_card` partial unique index against a direct SQL insert (I4.7). The concurrency proof (I4.6, looped 4×): one racer activates the open `DRAFT` while another rolls back a `SUPERSEDED` version — **both contend on `findActiveForUpdate`'s lock of the card's current `ACTIVE`**, so they serialize on that row lock; the winner commits, and the loser's `findActiveForUpdate` (READ COMMITTED) re-checks the now-`SUPERSEDED` old-active row, is filtered out, returns null, and its attempt to promote without demoting is refused by the partial unique index — so exactly one `ACTIVE` remains every iteration (the test uses `allSettled`, because that index rejection surfacing as a thrown transaction is the backstop working, not a bug). No deadlock: activate locks {draft, active}, rollback locks {target, active}, both acquiring the shared `active` row second.

## Recurring patterns (apply across units — not repeated per-unit below)

- **Permission-name ripple:** adding a name to `PERMISSION_NAMES` forces that key into every hardcoded `EffectivePermissionMap` object-literal fixture across ~25+ test files (`tsc`-caught for object literals, but a few hardcoded array-length assertions are not). See `[[permission-name-addition-ripple]]`.
- **Cross-schema integration-test ripple:** every pre-existing `tests/**/*.integration.test.ts` doing a fresh `DROP SCHEMA … CASCADE` + migrate cycle needs a `DROP SCHEMA IF EXISTS "<newschema>" CASCADE` added first — otherwise the next file's migration fails with "schema already exists." See `[[new-pgschema-integration-test-ripple]]`.
- **Audit event-type ripple (every write unit):** each new `AUDIT_EVENT_TYPES` entry needs (1) an `AUDIT_EVENT_CATEGORY_MAP` entry in `types/audit-log.ts` (`tsc`-caught) and (2) a bumped event-type count + optgroup assertion in `tests/components/audit-log-filters.test.tsx` (**not** `tsc`-caught). See `[[audit-event-type-addition-ripple]]`.
- **Repository mutation allow-lists:** the `*-repository-exports` and `*-module-boundaries` guardrails carry a per-write-unit allow-list entry — expected, not a surprise; add the entry in the same commit as the write.
- **New-route ripple:** `tests/app/route-manifest.test.ts`'s `ROUTE_MANIFEST` is a strict set-equality check against every real `app/**/page.tsx` — a new page 404-fails that test until its literal URL is added to the array.
- **Region/seam discipline:** a shell unit builds placeholder frames with `{/* pmXX */}` seam comments; each follow-up unit fills exactly one seam, leaving the others byte-unchanged (pm05→pm08, pm18→pm23, pm27→pm29/pm31/pm33).
- **`db → validation` ESLint boundary:** any `db/**` or `types/**` file that embeds a Zod-owned shape needs `"validation"` added to its allowed-import targets in `eslint.config.mjs` (first hit in pm02/pm03 — a forced companion change, not scope creep).

## Permanent lessons (from post-ship fixes — do not re-learn)

- **Grant-per-schema on deploy:** a deployed instance 500'd (`42501: permission denied for schema product`) because `bootstrap-db-roles.sql` only granted on `core` (pm09). **Any new schema must add its own grant/revoke block (incl. sequence grants) in the same change that adds its migration, and the file must be re-run**, or this recurs. See `[[db-role-bootstrap-per-schema]]`.
- **TOCTOU-safe status reads:** a status-gated branch/lifecycle decision must read its target's status on the transaction (`tx`, `FOR UPDATE`), immediately before the write — never from a pre-transaction `db` snapshot. This exact bug was found and fixed independently in pm14, pm15, pm16, and pm20; treat a pre-transaction status read as a review-blocking defect on sight (code-standards §1 rule 13).
- **Concurrency is proven, not assumed:** single-active-per-family (pm16), approve-vs-approve / approve-vs-reject (pm30), and suspend-vs-terminate (pm32) are each verified by live-DB races looped 4×. `inventory_status_history` "latest" ordering is by the sequence id, not `created_at` (fixed at transaction start, can invert under lock contention — pm32 fix). Concurrent same-family branches are serialized by `pg_advisory_xact_lock(hashtext(rootId))` in `resolveNextVersion` (pm16 fix).
