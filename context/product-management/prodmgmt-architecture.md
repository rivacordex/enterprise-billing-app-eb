# Product Management — Architecture (Module)

This document builds on `context/architecture.md`, which owns the platform-wide design — the technology stack, folder ownership, multi-module database design, the auth/authorization platform, storage principles and the platform invariants — and records **only what the Product Management module adds or changes**. Anything not stated here is inherited unchanged. This revision is scoped to the **Normalize Spec Characteristics & Price Components update**: the two `product` jsonb columns (`product_specifications.product_spec_characteristics`, `product_offering_price.price_component`) are replaced by six relational tables and one runtime read view. The Rate Card Lookup tables (`ratecard_version`, `RATECARD_RAN_USAGE_LKP`) are now part of the **baseline** and are restated only where this update depends on them.

**Status:** DESIGN. Proposal dated 2026-10-28 in `_updatemodule-product-normalize-spec-price-tables-plan.md` (authoritative). **Not built** — verified against the codebase on 2026-11-17: `db/schema/product.ts` still declares both jsonb columns, the six JSON CHECKs and `pricing_steps_ok()` still stand, migrations run to `0055`. **Owner decisions (plan §7 Q1–Q4): all four decided 2026-11-19 — recommendations accepted.** This document adopts the plan's recommendations — subtype tables + view (Q1), forward migration with verified backfill (Q2), `numeric(18,6)` money / `numeric(20,6)` quantity (Q3), keep `display_order` (Q4) — and must be re-read if any is decided otherwise. Changes to _Module Invariants_ require a documented design review; the amendments in §6 were **approved 2026-11-19** (project owner) with pm70 — one of them (Inv. #38) reverses a standing rule and carries its own G-N2 design-review record. **Storage built by pm70 (2026-11-19):** `0056_product_normalize_spec_price.sql` and the Drizzle mirror landed on the Part 6 feature branch; repositories, seeds and readers follow in pm71–pm74b.

**Last revised:** 2026-11-17. Supersedes the Rate Card Lookup revision of this document (recoverable at commit `0fc56cc`); that update's authoritative text remains `_updatemodule-ratecard-lookup-plan-v2.md` and specs `pm57a`, `pm58`–`pm68`.

**Baseline (delivered, carried forward unchanged):** five pages — View Product, Manage Products, Orders, Subscriptions, Rate Card; the five-value lifecycle `DRAFT → TESTING → ACTIVE → OBSOLETE → RETIRED`; the one-open / one-active expression indexes; the DRAFT guard `child_write_requires_draft` (`0040`) on `product_specifications` and `product_offering_price`; the retirement gate; the pricing-component **envelope as the API/UI contract** (`PricingComponent`, a Zod discriminated union of `strictObject` branches, pm47); the pm46a lane key (`0049`); the two rate-card tables and their three audit events. Module invariants **1–60** stand except where §6 amends them.

**Scope of this update.** Storage only. No new screen, no new permission, no new route, no Server Action or Zod change, no audit-shape change. The repository layer absorbs the whole change: it decomposes the envelope into rows on write and reassembles it on read, so nothing above `db/repositories/**` changes shape. The only user-visible difference is that specification characteristics render in **entry order** rather than the alphabetical order jsonb imposes today. Two non-application readers — the bill-run flow and the rating runtime — are rewritten to read a view instead of JSON paths and **must deploy in the same release**.

**Why subtype tables and not typed header columns (Q1).** The alternative — nullable `rate_per_unit` / `amount` / `committed_quantity` columns on the header — gives the same guarantees with less code **only if the four component types stay stable**. The pricing roadmap (rate-card-resolved price, negotiated override, N motivation bands) adds types and parameters; with subtype tables a new type is a new table and the header is untouched, and the view keeps runtime SQL exactly as simple as the alternative. Anyone proposing to flatten should read plan §6 first rather than re-deriving it.

**Every subtype table carries `component_type NOT NULL DEFAULT '<its type>' CHECK (component_type = '<its type>')` and `FOREIGN KEY (product_offering_price_id, component_type) REFERENCES product_offering_price (product_offering_price_id, component_type) ON DELETE CASCADE`.** This is the type-pinning pattern: a `pop_flat_fee` row for a `usage_rate` header is not rejected by a check, it is **unrepresentable**. A consequence worth knowing: because the FK is `NO ACTION` on update, a header's `component_type` **cannot change while a subtype row references it** — an edit that changes type must delete the subtype row, update the header, then insert the new subtype row, in that order, in one transaction.

### 3.4 Precision and normalization (Q3)

Today's JSON allows unlimited decimals; the plan caps money at `numeric(18,6)` and quantity at `numeric(20,6)`. Two facts make this an architecture rule rather than a column choice. **First**, Postgres rounds to the declared scale on insert without error, so a value with seven decimals would be stored changed and the envelope round-trip would silently differ from the input, the audit payload and the form — the cap must therefore be enforced at the **Zod boundary** so the database never has anything to round. **Second**, node-postgres returns the full declared scale (`"100.000000"`), so `toEnvelope` must strip trailing zeros back to the canonical money string or every audit diff changes. Inside the view, `steps[].ratePerUnit` and `aboveQuantity` are **JSON numbers** (today the envelope string); the capacity CTEs cast `::numeric` either way, and the view is a SQL-only contract — the envelope contract (money as a decimal string, Inv. #32) is unchanged for every application reader.

### 3.5 Migration and backfill (Q2)

`0056` is a **forward migration with a self-verifying backfill**: characteristics from `jsonb_each_text(...) WITH ORDINALITY` (ordinality becomes `display_order` — the one place today's alphabetical order is frozen into data), `price_type` and `pop_*` rows from `price_component`, steps from `jsonb_array_elements(price_component #> '{params,steps}')`, with `child_write_requires_draft` disabled for the backfill because released versions are write-protected. **The migration reassembles every envelope and every characteristic set and aborts on any mismatch before dropping anything**; only after that do the index swap, the CHECK and function drops and the two column drops run. The edit-in-place alternative (rewrite `0006` / `0040` / `0049`, rebuild the database) is plan §4 option A and is **not taken** unless Q2 is decided the other way — the rate-card delivery already set the forward-only convention for this module.

## 5. Background Tasks & AI

**None, in this update or any prior one. No AI/ML components anywhere in this module.**

- **The backfill is not a job.** It runs inside `0056` as a gated pipeline step before traffic shifts, verifies itself, and aborts the migration on mismatch. There is no post-deploy reconciliation task and no "backfill later" flag.

### New — introduced by the Normalize update

61. **The envelope is a projection, never a record.** No column in any schema stores a `PricingComponent` or a characteristics object. `toEnvelope` / `fromEnvelope` in `db/repositories/product-offering-price.ts` are the **only** translation points; no service, action, seed, test helper or flow assembles or decomposes an envelope.
62. **A subtype row attaches only to a header of its own type, structurally.** Every `pop_*` table carries a pinned `component_type` and a composite FK to `(product_offering_price_id, component_type)`. The mismatch is unrepresentable, not validated — a test that tries to insert one must get an FK violation, not an application error.
63. **Every committed header is complete.** A header has its subtype row, and a `capacity_motivation` header has at least one step, at COMMIT — enforced by the deferred constraint trigger. The repository writes header and children in **one transaction**; no code path commits a header alone, and deleting the last step of a `DRAFT` motivation without replacing it fails at COMMIT.
64. **The reference tables are system data.** `price_component_type` holds exactly four rows and `price_component_price_type` exactly five, seeded by migration. `app_runtime` holds no DML on them. A new component type or `(type, priceType)` pair is a committed migration **and** a reviewed design — never a UI, never a seed script.
65. **Derived fields are never stored.** `specVersion`, `appliesAt`, `basis`, `boundTo` and `usage_rate`'s `plaSpecId` are computed on read — from `price_component_type`, from the row's `unit_of_measure`, and from `rate_card_lookup IS NOT NULL`. A column that persists any of them is a defect; the PC10/D4 pairing rule is now unrepresentable rather than refined.
66. **Characteristics keep entry order.** `display_order` is `1…n`, contiguous per specification, `UNIQUE (product_spec_id, display_order)`; every read orders by it; `{}` writes no rows. A reader that sorts by `char_name` reintroduces the defect this update removes.
67. **Non-application runtimes read prices only through `product.offering_price_v`.** `billrun_runtime` and `rating_runtime` hold `SELECT` on the view and **nothing** on `pop_*` or the reference tables; `reporting_runtime` holds nothing new. The view is owner-privileged (no `security_invoker`) so the view grant is the whole surface. No flow definition and no worker module names `price_component` or joins a `pop_*` table.
68. **The database never rounds a price.** Money is `numeric(18,6)` and quantity `numeric(20,6)` at rest; Zod rejects more than six decimals **before** a row exists, and `toEnvelope` strips trailing zeros on read. `toEnvelope(fromEnvelope(x))` deep-equals `x` for every valid input — the round-trip is the test, and silent rounding is the failure it exists to catch.
69. **The DRAFT guard covers every child and grandchild.** `child_write_requires_draft` fires on the five new tables; a grandchild resolves its offering through its parent (spec or header); the parent-gone branch passes so a discarded `DRAFT` / `TESTING` version cascades offering → header → subtype → steps with no orphans. Any write to any of the five tables under a non-`DRAFT` version fails with SQLSTATE `23514`.
70. **A header's `component_type` is immutable while a subtype row references it.** The composite FK is `NO ACTION` on update, so a type change is delete-subtype → update-header → insert-subtype in one transaction, never an in-place `UPDATE` of `component_type`. A `price_type` change within the same type (e.g. `recurring` → `oneTime`) is permitted by the FK and still subject to the unit/period CHECKs and the DRAFT guard.
71. **The backfill is verified or it does not ship.** `0056` reassembles every envelope and characteristic set and **aborts on any mismatch before dropping a column, CHECK or function**. The two jsonb columns are dropped in the same migration, after verification. `0006`, `0040` and `0049` are never reopened for this change.
72. **The readers ship with the schema.** `bill_run_processing.template.yml`, its `local-dev/` copy and `rp.py` deploy in the **same release** as `0056`. A release containing one side without the other is a broken release, not a staged one — recorded as a deployment rule because no test can catch it after the fact.
73. **Branching copies grandchildren exactly.** `branchOfferingAsDraft` copies every characteristic (same `display_order`), every subtype row and every step under the new header ids, and the reassembled envelopes on the branch deep-equal the source version's. A branch that loses a step or reorders a characteristic is a defect.
