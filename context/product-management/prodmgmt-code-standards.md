**New with the Normalize update**

48. **(normalize) The update changes storage and adds a raw quantity check in the existing price form (§1.53).** No other file under `app/(app)/products/**`, `components/products/**` or `actions/product/**` changes. `EXPECTED_PRODUCT_ACTION_FILES` stays at 17. Specification characteristics render in **entry order**, and reopened prices show canonical money text.
49. **(normalize) `toEnvelope` and `fromEnvelope` live in `db/repositories/product-offering-price.ts` and nowhere else** (Inv. #61). `toEnvelope(header, children)` returns a `PricingComponent` and passes the assembled object through `persistablePricingComponentSchema` exactly as today's read path does — a row set that fails to parse is corruption and **throws**, never renders a partial card. `fromEnvelope(component)` returns the header's `price_type` plus the one subtype row or the step rows. Neither is exported from `types/`, neither is imported by a service, and no seed, fixture or flow re-implements either.
50. **(normalize) A price write is header then children, one transaction, in this order.** Insert: header `RETURNING product_offering_price_id` → subtype row or step rows. Update on a `DRAFT`: when `component_type` is unchanged, update the header and **replace** the subtype row (steps: `DELETE` then `INSERT`); when it changes, **delete the old subtype row first, then update the header, then insert the new subtype row** — the composite FK is `NO ACTION` on update and refuses a header type change while a child references it (Inv. #70). The deferred completeness trigger makes the mid-transaction state legal; the order above is what makes the FK happy.
51. **(normalize) Zod is still the primary guard, and a database refusal of a state Zod already rejects is thrown, not mapped.** The Zod union already refuses an unseeded `(component_type, priceType)` pair, a motivation with zero or duplicate steps and a missing parameter, so the composite FK, the step PK and the deferred trigger can only fire when Zod was bypassed — that is corruption and it fails loud (general §1.12). **No new typed result code is added** for them, and no `23514` / `23503` translation is introduced. The one DB collision the services translate today — `isUniqueViolation(err, "product_offering_price_lane_start_unique")` → `DUPLICATE_START` — keeps working because the lane index **keeps its exact name** (§6.34). _Note: `prodmgmt-update-overview.md`'s flow step 5 says these surface "through the same error mapping the module uses for `23514` today"; no such mapping exists in the codebase (`lib/db-errors.ts` exports the `isUniqueViolation(err, constraintName)` the price services import; `db/errors.ts`'s argument-less `isUniqueViolation(e)` is not used by them — citation corrected in pm71). This rule is the standard; the overview sentence was corrected on 2026-11-17 (Appendix A, A25)._
52. **(normalize) Money read from `numeric` is normalized by one pure helper before it enters an envelope.** `toEnvelope` applies `canonicalDecimalString` in `lib/decimal-string.ts` to each money field. It removes redundant leading integer zeros and trailing fractional zeros, including a decimal point left behind; it preserves significant digits and never rounds or parses money to `number`. `"000100.00"` and the database’s `"100.000000"` both become `"100"`. Quantities are read back as `Number(value)` after the same normalization.
53. **(normalize) Validate precision before storage.** `moneyStringSchema` matches `^\d{1,12}(\.\d{1,6})?$` and preserves accepted input text (including `"100.00"`). `toEnvelope` canonicalizes money on read; audit before and after snapshots are both built from these canonical reads (§1.63). The form rejects exponent notation and more than six fractional digits in `committedQuantity` and `aboveQuantity` before conversion. Zod also checks that `String(n)` matches `^\d{1,14}(\.\d{1,6})?$`; after conversion it cannot distinguish `1e3` from `1000`.
54. **(normalize) Seeds and test fixtures write prices and characteristics through the repository, never into the new tables directly.** No `tx.insert(popFlatFee)`, no `INSERT INTO product.pop_*`, no `INSERT INTO product.product_spec_characteristic` outside `db/repositories/**` and the migration backfill. The raw-SQL price fixtures that exist today (`tests/db/helpers/billrun-capacity-pricing-fixtures.ts`, `tests/fixtures/reporting/polygon-capacity-seed.ts`, `tests/fixtures/reporting/gl-feed-seed.ts`) are rewritten to call `productOfferingPriceRepository.insertPrice` (or one shared fixture helper that does). A fixture that writes a header without its subtype row is exactly the incomplete state Inv. #63 forbids, and it would fail at COMMIT anyway.
55. **(normalize) Characteristics are written in the order they arrive and read in the order they were written.** The repository writes `display_order = 1…n` from `Object.entries(parsed)` of the validated `Record<string,string>`; `{}` writes no rows; an update **replaces** the row set (`DELETE` then `INSERT`) inside the transaction; the read builds the object with `Object.fromEntries(rows ORDER BY display_order)`. **Recommended tightening, not in the plan:** the Zod record schema rejects a characteristic name matching `^\d+$`, because JavaScript hoists integer-like keys to the front of `Object.entries` regardless of insertion order and would silently reorder them. **Built 2026-11-19 (pm69 D5):** `productSpecCharacteristicsSchema`'s key schema refuses `^\d+$` with "Characteristic name must not be all digits"; `validation/characteristics.schema.ts` (ordering/inventory) is deliberately unchanged.
56. **(normalize) Three files outside this module change in the same release, each under its own authorization recorded in the unit spec:** `workflow-management/flows/bill-run-processor/bill_run_processing.template.yml`, its `local-dev/bill_run_processing.yml` copy, and `workflow-management/worker/workflow-engine/runtime/rp.py`. The rewrite is **mechanical** — `(pop.price_component #>> '{params,amount}')::numeric` → `pop.amount`; `price_component ->> 'priceType' = 'recurring'` → `pop.price_type = 'recurring'`; the `lead()` partition gains `price_type` in place of the `CASE` term — and touches no business logic. A unit that changes proration, rounding, the BAN grain or rating's card-driven detection has left scope. The flow and the worker image **deploy with `0056`**, never before and never after (Inv. #72).
57. **(normalize) The reference tables are system data: four rows and five rows, seeded in `0056`, read-only to the application.** No UI, no Server Action, no service and no seed script writes `product.price_component_type` or `product.price_component_price_type`; `app_runtime` holds no DML on them (§6.42). A new component type or pair is a committed migration **and** a reviewed design (Inv. #64).
58. **(normalize) Two columns named `price_type` exist in the database and are never equated.** `product.product_offering_price.price_type` carries the TMF axis and is typed `EnvelopePriceType`; `ordering.order_item_price_override.price_type` carries the ordering module's `OverridePriceType`. No join, no mapping function, no shared union, no `COALESCE` across them, and no test fixture that writes one from the other. `services/ordering/order-preconditions.ts` keeps resolving the override lane from the **envelope** it receives, exactly as pm56b left it.
59. **(normalize) Derived fields are computed, never stored, and `toEnvelope` is the only place that computes them for the app.** `specVersion` is the constant `1`; `appliesAt` and `basis` come from `price_component_type`; `boundTo` is `{ unitOfMeasure }` from the header's `unit_of_measure` for the three quantity-based types and `null` for `flat_fee`; `plaSpecId` is `price_component_type.pla_spec_id` for the capacity types, `null` for `flat_fee`, and `'PLA_USAGE_RATE'` for `usage_rate` **iff** `rate_card_lookup IS NOT NULL` (Inv. #65). The view computes the same `pla_spec_id` for SQL readers; the two derivations are asserted equal by the parity tests, not by sharing code.
60. **(normalize) `branchOfferingAsDraft` copies grandchildren by row, with an id map, never by envelope round-trip.** Insert the new headers `RETURNING` ids, build `Map<oldHeaderId, newHeaderId>`, then copy `pop_*` rows and `pop_motivation_step` rows column-for-column under the new ids; copy `product_spec_characteristic` rows the same way under the new spec ids, `display_order` preserved. Routing the copy through `toEnvelope`/`fromEnvelope` would re-normalize values and is forbidden in production code; the **test** asserts that the reassembled envelopes on the branch deep-equal the source's (Inv. #73).
61. **(normalize) The detail page's prices load in one relational query.** `productOfferingPriceRepository.findByOfferingIdWithDerivedEnd` uses `db.query.productOfferingPrice.findMany({ with: { usageRate, flatFee, capacityCommitment, motivationSteps } })` — the module's (and the codebase's) first `relations()` usage (§2.27). §1.16's fan-out ban extends to subtype loads: **never one query per price row to fetch its subtype**, and never a `Promise.all` over headers.
62. **(normalize) The view is for non-application runtimes only.** No file under `app/**`, `actions/**`, `services/**`, `db/repositories/**`, `db/seeds/**` or `tests/**` (other than the grant and parity tests that name it) selects from `product.offering_price_v`. The application reads the tables through the repository; the engine reads the view by grant (Inv. #67). The view is **not** declared in `db/schema/product.ts` — it is SQL-of-record, and declaring it would invite an application reader.
63. **(normalize) Audit payloads keep their shape and use canonical money text.** `PRODUCT_PRICE_ADDED` / `_UPDATED` / `_DELETED` carry `componentType` plus the **reassembled** envelope in `beforeData` / `afterData`, built by `toEnvelope` on rows read inside the same transaction; the specification events carry the reassembled `Record<string,string>`. No new event type, no `AUDIT_EVENT_TYPES` or `AUDIT_EVENT_CATEGORY_MAP` change, no `audit-log-filters.test.tsx` count change (§6.18 of the `0fc56cc` revision does not fire).

## 6. Data and Storage Rules (module-specific)

Items **1–34** of the `0fc56cc` revision stand except as amended here. **Amended:** §6.1 / §6.23 (table count — §6.35), §6.3 (effectivity end is derived per the plain-column lane — §6.34), §6.4 (lane key — §6.34), §6.5 (completeness is no longer a CHECK — §6.37), §6.8 (the DRAFT guard **is** modified, extended to five tables — §6.38), §6.12 (JSONB guard — two fewer columns; still binds `reject_summary`), §6.14 (`0006` stays locked; the authorization question does not arise because this is a forward migration — §6.40), §6.19 (the drops this update adds — §6.41), §6.20 (the header's columns — §6.33). **Does not fire:** §6.18 (no new audit event type), §6.21's "no bootstrap role change" (this update **does** change grants — §6.42), §6.22 (one-shot on one branch stays true; the full-suite-green claim is made once, at the ship gate).

**§6.34 — C14 decided 2026-11-19 (pm70 D7):** the lane key **stays a unique index**, created in SQL with `NULLS NOT DISTINCT` under the unchanged name `product_offering_price_lane_start_unique`, now on five plain columns `(product_offering_id, component_type, unit_of_measure, price_type, start_date_time)`. `services/product/insert-price.ts` maps a `23505` on that name to `DUPLICATE_START`; keeping the object kind keeps the error's `constraint` field identical. A `unique().nullsNotDistinct()` constraint was considered and rejected because it changes the object kind under a name the service keys off. In Drizzle it is `uniqueIndex(...).on(...)`; `NULLS NOT DISTINCT` is SQL-only (drizzle-orm 0.45 has no `nullsNotDistinct()` on `uniqueIndex()`) and guardrail 13 asserts it in `pg_indexes`.

35. **(normalize) The module owns eleven tables and one view, all in the `product` schema:** `product_offering`, `product_specifications`, `product_offering_price`, `ratecard_version`, `RATECARD_RAN_USAGE_LKP`, and the six new — `product_spec_characteristic`, `price_component_type`, `price_component_price_type`, `pop_usage_rate`, `pop_flat_fee`, `pop_capacity_commitment`, `pop_motivation_step` — plus the view `offering_price_v`. **This amends §6.23**'s "five tables" (Appendix A, A15). Table names are `snake_case`, singular for the new tables (the plural `product_specifications` is legacy and not a precedent).
36. **(normalize) Every subtype table carries the type-pinning pattern, exactly:** `product_offering_price_id text`, `component_type text NOT NULL DEFAULT '<its type>' CHECK (component_type = '<its type>')`, and `FOREIGN KEY (product_offering_price_id, component_type) REFERENCES product.product_offering_price (product_offering_price_id, component_type) ON DELETE CASCADE`. The 1:1 tables use `product_offering_price_id` as PK; `pop_motivation_step` uses `(product_offering_price_id, above_quantity)`. The FK target is the **new** `UNIQUE (product_offering_price_id, component_type)` on the header (§6.33). No subtype table carries `currency`, `unit_of_measure`, `start_date_time` or any other header column.
37. **(normalize) Completeness is one PL/pgSQL function and five constraint triggers, all `DEFERRABLE INITIALLY DEFERRED`.** `product.price_header_is_complete()` locks the header with `FOR NO KEY UPDATE` while reading its `component_type`, then checks: `usage_rate` → a `pop_usage_rate` row; `flat_fee` → a `pop_flat_fee` row; `capacity_commitment` → a `pop_capacity_commitment` row; `capacity_motivation` → **at least one** `pop_motivation_step` row. Triggers: `product_offering_price_complete_ct` (`AFTER INSERT OR UPDATE ON product_offering_price`) and `pop_usage_rate_complete_ct`, `pop_flat_fee_complete_ct`, `pop_capacity_commitment_complete_ct`, `pop_motivation_step_complete_ct` (`AFTER UPDATE OF product_offering_price_id OR DELETE`, resolving the header by `OLD.product_offering_price_id`; **if the header no longer exists, pass** — that is the discard cascade). On violation `RAISE EXCEPTION … USING ERRCODE = '23514'`, the same code the DRAFT guard uses. `product.pricing_steps_ok(jsonb)` is dropped in the same migration.
38. **(normalize) `child_write_requires_draft` is extended, not forked.** The `0040` function gains branches keyed on `TG_TABLE_NAME` for the five new tables; a grandchild resolves its offering through its parent — `product_spec_characteristic` via `product_specifications.ref_product_offering_id`, the four `pop_*` tables via `product_offering_price.product_offering_id` — and the **"parent not found → pass"** branch is kept so the cascade offering → header → subtype → steps still completes. Five new `BEFORE INSERT OR UPDATE OR DELETE` triggers named `<table>_draft_guard`, matching `product_offering_price_draft_guard`. Each branch reads only columns the firing table has (the `0040` comment explains why one `CASE` across tables fails to plan). A direct write under a non-`DRAFT` version fails with `23514` on every one of the five tables.
39. **(normalize) Constraint and index names are explicit and ≤ 63 bytes** (general §6.19). Drizzle's derived FK name for the subtype FKs — `pop_capacity_commitment_product_offering_price_id_component_type_fk` — is **67 bytes** and would be truncated, so every new constraint is named by hand in the SQL, the Drizzle mirror and the snapshot alike:

    | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
