## Architecture Decisions

- **2026-08-28 — flow definitions (`flows/**`) also live in `enterprise-billing-app`, resolving the question the 2026-08-27 decision below deliberately left open.** rm06 is the first unit that ships real Kestra flow definitions, and both `specs/rm06-flow-template-logging-sweep.md`'s header ("Repo: rating repo") and `ratemgmt-ai-workflow-rules.md` (§ "Read this first", §1.2, §2.2, §2.6, §6) repeatedly frame flows as living in a genuinely separate repository from the app — stronger and more repeated language than rm04's infra-only framing. Rather than either build a new repo no one had asked for yet, or silently reuse the rm04 precedent without re-confirming it now applies to business-logic flows too, the user was asked directly (`AskUserQuestion`): create a real separate repo, or keep flows here. **Chosen: keep them here.** Landed as `rating-engine/flows/` (a new sibling of the existing `rating-engine/{worker,kestra,dev}/` subtree), and `infra/azure-pipelines.yml` gained a `deploy_rating_flows` stage rather than a second repo's own pipeline. This does not retroactively resolve every reference to "the rating repo" throughout the rm0x specs — later units should keep reading "rating repo" as "the `rating-engine/` subtree of this repo," matching how `rating-engine/worker/Dockerfile` and `rating-engine-container-app.bicep` were already read that way for rm04/rm05.
- **2026-08-27 — rm04's infra lives in `enterprise-billing-app`, not a separate "rating repo."** The spec (`rm04-spec` header table, D1) and `ratemgmt-code-standards.md` §8/§1.2 both frame `worker/**`/`infra/**`/`dev/**` as a separate rating-repo boundary, kept apart from the app repo because rating *flow logic* must never live here (`ratemgmt-ai-workflow-rules.md` §1.2). Asked directly, the user clarified: their notion of "rating repo" is specifically the future home of Kestra **flow definitions** (the actual business logic, rm06+), and that repo does not need to exist yet — flows aren't being built in this pass. The Kestra **engine deployment** (worker image, Bicep, local compose) is infrastructure for standing up the app's own Kestra instance, so it belongs in the existing app codebase. Landed as a `rating-engine/` subtree (`worker/`, `kestra/`, `dev/`) plus new modules under the existing `infra/bicep/modules/` (rather than a parallel `infra/` tree), keeping one Bicep deployment graph that references the same shared ACR/Key Vault/Container Apps Environment/Postgres as the rest of `main.bicep` (D1's "shared platform footprint"). **This is a deviation from the literal spec text**, recorded here per `ratemgmt-ai-workflow-rules.md` §5.5 since `_newmodule-rating-engine-plan.md` (the code-standards §7 owning document for "design decision and its reasoning") is not present in this repo, mirroring the already-known `rm00-build-plan.md` gap. When flow work actually starts, a real separate rating repo (or a decision to keep flows here too) needs to be made then — this decision does not resolve that, only defers it honestly instead of building a repo no one asked for yet.
- **2026-08-27 — D0 encoded as a deploy gate, not just a doc note.** Rather than either refusing to write any rm04 code (honoring D0 "do not build the rest of this unit" with maximal literalness) or writing it and hoping someone remembers not to deploy it, `infra/bicep/main.bicep`'s `deployRatingEngine` param defaults to `false` and gates every rm04-specific resource (storage account, Container App). The files exist, compile, and are ready, but a normal `az deployment group create` against these parameter files does not stand up the engine — someone has to deliberately flip the flag, which is the natural point to also confirm the spike passed.
