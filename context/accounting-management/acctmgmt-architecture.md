# Accounts Module — Architecture

This document extends the platform-wide `context/architecture.md` — everything there (stack, folder boundaries, shared-core database design, Better-Auth/RBAC platform, Platform Invariants #1–18) applies unchanged; only Accounts-module **differences and additions** are recorded here. Functional decisions trace to `_newmodule-account-plan.md` (Q1–Q28) and `acctmgmt-project-overview.md`; the Transactions-page revision traces to `_updatemodule-accounts-transactions-plan.md` (D1–D7) and `acctmgmt-update-overview.md`.

**Status:** ACTIVE (planning-complete; Transactions revision planning-complete). **Users:** Revenue Operations. **Schema:** `billing`.

## What the Transactions revision changes architecturally

Almost nothing, deliberately. It adds **one read path** (document list + per-document lines), **one client-side behaviour** (nav links propagating selection context), and **no tables, columns, migrations, permissions, document types, services with write access, or runtime components**. Every architectural delta below is marked **(D#)** against its decision. Items marked _unchanged_ are restated only because the revision touches the same surface and the boundary must stay explicit.

## 3. Storage model

All in Postgres, `billing` pg schema. No file storage (journal export streams CSV from a live query, logged to `core.AUDIT_LOG`), no cache (Platform Inv. #15 extended: **balances are never cached or stored** — always read from `pgledger_accounts_view`).

**The Transactions revision adds no storage.** No new table, column, index requirement beyond what the list query needs for its existing filter columns, migration, or seed. Everything the workbench displays already exists in `billing.document` and `billing.document_line`; the revision only reads it.

### Document-list scope predicate (D2)

The workbench is BAN-scoped, but **four services write `refBillingAccountId: null`** — `capture-payment.ts`, `capture-deposit.ts`, `reverse-deposit.ts`, `refund-deposit.ts`. These are FA-level documents by design. A literal `ref_billing_account_id = :ban` filter would hide every payment capture and every deposit, including the page's most common output. The scope predicate is therefore:

```sql
WHERE ref_financial_account_id = :fa
  AND (ref_billing_account_id = :ban OR ref_billing_account_id IS NULL)
```

With no BAN selected, the second clause is dropped and the query is **FA-wide**: every document for the FA is returned regardless of BAN assignment, consistent with the page's existing gating, which enables `CapturePaymentPanel` on `financialAccountId` alone. When a BAN is selected, documents belonging to a _different_ BAN under the same FA are excluded; the cross-BAN view lives in Accounts Overview and Ledger Explorer.

ID convention follows platform §3 (prefix + zero-padded sequence); pgledger keeps its own prefixed ULIDs (`pgla_`, `pglt_`).

## 4. Auth & access model

Platform RBAC unchanged (Better-Auth, code-seeded registry, READ/EDIT/DELETE levels, union-highest-wins). Module permissions (Q7/Q20) — **unchanged by this revision; no permission added, split, or re-scoped:**

| Permission              | Grants                                                                                                                                     | Typical holder                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| `accounts-view`         | Accounts Overview, Ledger Explorer; read-only everywhere in the section                                                                    | All RevOps                              |
| `accounts-transactions` | Transactions page: draft/submit documents; post at/below the reason code's `auto_post_limit`; MANAGER additionally approves/posts above it | RevOps USER / MANAGER                   |
| `accounts-config`       | Chart of Accounts, GL Journal export, period close, Administration → Accounts Settings                                                     | RevOps MANAGER / finance-config holders |

Workflow rules enforced **server-side in `services/accounts/`**, independent of nav visibility: threshold routing per reason code; **`approved_by ≠ created_by`** on every approval; sensitive reason codes (`DEP_REVERSE`, `DEP_REFUND`, `BAD_DEBT_WRITEOFF`) seeded with limit 0 = always four-eyes. Ownership: documents belong to the module, not the creator — any permitted MANAGER may approve (except the creator).

### READ vs EDIT in the workbench (D4/D5)

The revision makes the READ/EDIT split more visible, without changing what either grants:

| Holder                           | Sees                                                                                                                 | Does not see                                                                       |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `accounts-transactions` **READ** | Documents table, filters, detail drawer, document lines, posted legs                                                 | Action bar, reversal control, approve/reject — no write affordance rendered at all |
| `accounts-transactions` **EDIT** | All of the above plus the action bar, the reversal control on eligible documents, and approve/reject on pending ones | —                                                                                  |

**Line-level reversal carries no separate gate (D5).** `reverseDocument` and `reverseLine` require the same permission, matching what the services already enforce; the line checkboxes select between them without a privilege change.

**Affordance visibility is not authorization.** Hiding the reversal control on ineligible documents (D4) is a UI decision about clutter, not a security boundary — `reverseDocument` / `reverseLine` still validate state, line coverage, FA ownership, concurrency and period independently and return `DOC_STATE_INVALID`, `ALREADY_REVERSED`, `WRONG_FINANCIAL_ACCOUNT`, `CONFLICT` or `PERIOD_CLOSED` regardless of what was rendered.

## 5. Background tasks & AI

**None — deliberately, and the Transactions revision adds none.** No AI/ML. No scheduled jobs:

- **No overdue scheduler** — overdue is derived at read time from open A/R + resolved terms (Q8/Q14).
- **No bank webhooks / statement import** — all captures manual (Q21/Q22).
- **No auto cash application** — allocation is manual document lines (Q24).
- **No bill run** — charges are manual DBNs until the Invoicing module (Q8).
- **No background indexing, prefetch, or materialisation for the workbench (D2)** — the document list is a request-scoped, paginated query executed during the page's Server Component render. Nothing is precomputed, warmed, or invalidated.
- GL export and trial balance are live queries executed on user action, not batch outputs.

Period close is a user-initiated `accounts-config` action, not a job. If later phases add jobs (bill run, dunning), they follow platform §6 (Container Apps Jobs, dedicated Managed Identity).

## 6. Module invariants

Additions to Platform Invariants #1–18; each is testable and CI-enforced. Invariants #1–14 are from the original module build (plan Part A §4 tests in parentheses); **#15–21 are added by the Transactions revision (D1–D7)**.

1. **Zero-sum ledger.** `Σ balance = 0` per currency across all `billing` pgledger accounts after every committed transaction. (V1)
2. **No stored balances.** No module table column ever holds a monetary balance; every balance, badge, and utilisation figure is computed from `pgledger_accounts_view` / `pgledger_entries_view` at read time. (V3)
3. **Money moves only through posted documents.** Every ledger transfer is created inside a document-posting transaction and carries `metadata.doc`; every posted `document_line` has exactly one `pgledger_transfer_id` (UNIQUE). No UI, action, or service calls transfer functions outside document posting. (V11)
4. **The ledger is append-only.** pgledger tables are never UPDATEd/DELETEd by application code; repositories touch pgledger only through its functions and views. Corrections are reversal documents with opposite legs (extends Platform Inv. #18). (V13)
5. **Document posting is atomic.** Doc state change + all transfers + audit entry commit in one DB transaction; any failure rolls back everything. (V7)
6. **Approver ≠ creator, thresholds server-side.** A document above its reason code's `auto_post_limit` cannot reach `posted` without an approval by a MANAGER who is not `created_by`; the check lives in the service, never only in the UI. (V11)
7. **Closed periods reject postings.** Every post validates `event_at` against `billing.accounting_period`; closed → error with re-date guidance. No force-post, no silent rerouting, no reopening. (V11, Q9)
8. **Posting nature steers the counter-account.** The sys account for every non-customer leg is selected from the reason code's `posting_nature` (Q19) — never hard-coded per page, never chosen by the user. (V12)
9. **Binding completeness.** Every BAN has exactly one `receivables` binding; every FA exactly one `unapplied_cash` and one `deposits` binding; binding currency = owner currency = pgledger account currency. (V2)
10. **GL resolution is total and unambiguous.** Every pgledger account resolves to exactly one postable GL code; unmapped count must be 0 before any journal export; `Σ debit = Σ credit` in every exported period. (V5, V6)
11. **Catalogs retire, never delete.** `bill_cycle`, `reason_code`, `gl_account` rows referenced by history are never deleted; state → `retired` removes them from selection, not from joins. (V9)
12. **Closure requires zero.** BAN closes only at A/R = 0; FA closes only when unapplied = 0, deposits = 0, and all BANs closed. (V14, Q11)
13. **Terms freeze at issuance.** Resolved term = `coalesce(BAN override, cycle default)` at document time; issued documents never re-derive when catalog or override later change. (V10, Q14)
14. **Fork integrity.** The pgledger SQL in migrations is transform-script output from the vendored upstream file at the recorded commit hash — never hand-edited. (Q10)
15. **The workbench read path never writes.** `services/accounts/list-transaction-documents.ts` and the document-list repository method issue SELECTs only — no INSERT, UPDATE, DELETE, no transaction, no call into `post-document.ts` or any pgledger function. Adding a write to the read path is a boundary violation, not an optimisation. **(D2)**
16. **BAN-scoped document queries must admit FA-level documents.** Any query narrowing documents by billing account includes `OR ref_billing_account_id IS NULL` under an FA constraint. A predicate of the form `ref_billing_account_id = :ban` alone is a defect — it silently hides payment captures and all three deposit document types. Regression-tested by asserting a `PAY` capture and a `DEP` capture are both returned when a BAN is selected. **(D2)**
17. **Selection context is URL-derived and nav-preserved.** `party`/`fa`/`ban` live only in search params, parsed through `parse-accounts-context.ts`; they are never held in component state, session storage, cookies, or a context provider. Every Accounts nav link propagates them — a link that drops the context is a defect, tested by asserting all five hrefs carry the params. **(D7)**
18. **UI eligibility mirrors service validation; it never replaces it.** The reversal control renders exactly where `state === "posted"` and at least one line has `reversedByLineId === null`, matching `reverse-document.ts`. Hiding or showing a control changes no server behaviour: the service re-validates state, line coverage, FA ownership, `lastModified` concurrency and period on every call, and its error codes are unchanged by this revision. **(D4)**
19. **Document type is closed; reversals reuse the original's type.** The five types (`PAY`, `DEP`, `CRN`, `DBN`, `ADJ`) are exhaustive — no "reversal", "refund" or "write-off" type exists. A reversal inserts a document of `doc.docType`, and sub-actions are distinguished by reason code only. Any filter, badge, or label implying a sixth type is a defect. **(D2)**
20. **Dialog wrapping preserves panel contracts.** Moving a create-panel into a `Dialog` changes only its shell. Props, Zod schema, server action, error mapping and submit semantics are byte-identical; a panel must remain renderable outside a dialog. Behaviour changes belong in their own change, not in the restructuring. **(D3)**
21. **Reversal approval weight is inherited, never re-derived.** A reversal routes through the same threshold logic as its original's reason code; the UI states this before submission but does not compute it. The approval decision remains `services/accounts/`'s alone. **(D4)**
