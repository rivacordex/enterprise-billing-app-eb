# Billing Management (Bill Run) Module — Architecture

This document **extends `context/architecture.md`** (the platform-wide architecture every module inherits — stack, folder boundaries, storage principles, multi-module DB design, the auth platform, and the 18 platform invariants) and records **only what the Bill Run module adds or does differently**. User flows and the functional design live in `billmgmt-project-overview.md` and `billmgmt-update-overview.md`; the phase-3 design decisions are in `_updatemodule-billing-billrun-phase3-plan.md`; the workflow/rating seam is in `_newmodule-billrun-rating-workflow-plan.md`; the shared engine platform is in `workflow-management/wfm-architecture.md`.

**Status:** Phase 3 planning — **ENG CLEARED** (`/plan-eng-review`, 2026-09-14; see `_assessment-gstack-review-report-billrun-phase3.md`). Every platform invariant in `architecture.md` §7 is inherited unchanged; the rules in §6 below are additional and module-specific. Module invariants run 1–28; **#15 is a retired tombstone** (D31) and is never reused.

**One-line summary of the deltas:** the module introduces (1) an **external workflow engine** (Kestra OSS) that orchestrates the pipeline and drives the app through the platform's first **machine-to-machine ingest path**, (2) **partitioned high-volume record tables** maintained by `pg_partman`/`pg_cron`, (3) a **two-writer boundary** in which a least-privilege engine role computes bill data while the app remains sole writer of run-state and posting, and (4) **`billing.customer_bill_line` as the bill's stored charge record**, assembled from more than one source.

## 1. Stack — module additions

Everything in `architecture.md` §1 still holds (Next.js + Route Handlers/Server Actions over `services/`, Drizzle on Azure Flexible Server PG 17, Better-Auth, Container Apps, no cache/CDN). The Bill Run module adds:

| Layer | Technology | Role |
| --- | --- | --- |
| **Workflow orchestration** | **Kestra (OSS edition)** — external, reached through the named engine registry (`billrun`) | Runs the bill-run **compute plane**: `bill_run_processing` (validation → collection → aggregation → taxation → verification, fanned out per account) and `bill_run_distribution` (transport). **Not an app process** — it drives the app via M2M ingest. Schema and code stay vendor-neutral (`workflow_execution_id`, `workflow_definition_id`); Kestra is named only here, in `wfm-architecture.md`, and in the plan's §8. |
| **Compute role** | **`billrun_runtime`** Postgres role | The engine's own least-privilege identity. Writes `customer_bill`, `customer_bill_tax_item`, **`customer_bill_line`**, and the six claim columns on `rating.udr_rated`. Cannot touch run-state, `billing.document` or pgledger. |
| **Table partitioning** | **`pg_partman` + `pg_cron`** on Azure Flexible Server | Monthly range-partitioning on `period_partition`; daily maintenance (premake + detach-and-archive at the 7-year boundary) driven by a `partition_management` config table. A **DB-level scheduler, not an app job.** |
| **Ledger posting** | **pgledger + the Accounts document engine** (`postDocument`, `INV` documents) | **Reused, not owned.** One `INV` per billed account inside the app's own transaction; the INV reason code carries an unlimited `autoPostLimit` so it auto-posts without per-document approval. |
| **Usage charge source** | **`rating` schema** (`rating.udr_rated`) — external, real | Already-rated Usage Detail Records, produced by the rating engine's file-batch pipeline (`RAN_USAGE`). Bill Run **reads** and **claims**; the rating engine owns everything else. |
| **Recurring charge source** | **`inventory.product_inventory`** — external, read-only | Subscriptions active in the period. Recurring charges are **derived by the bill run**, priced as-of against `product.product_offering_price` with `ordering.order_item_price_override` applied. They never enter `rating.udr_rated`. |
| **Recurring price resolver** | **New compute, owned by the flow** | Not a reuse of rating's usage resolver (`rp.py` is usage-only and refuses tiered). It resolves `price_type='recurring'` as-of, maps `recurring_charge_period_length`/`_type` onto the bill cycle, multiplies by `product_inventory.quantity`, and carries an explicit tiered / lookup-miss policy. "No product-module change needed" refers to the **catalog schema**, never to the compute. |
| **Document rendering** | **Playwright / headless Chromium** (`node:22-bookworm-slim` image) | Draft PRO-FORMA preview (on-demand, watermarked, never stored) and the final per-account invoice PDF. |
| **Artifact storage** | **Azure Blob** (`invoices/` container); **Azurite** in local dev | Final invoice PDFs (immutable, checksummed) and the transient per-run report CSV. |
| **Distribution transport** | **SFTP** via Kestra plugins (`fs.sftp.Upload`, `azure.storage.blob.Download`, `core.http.Request`) | One PUT per invoice PDF plus the run report. Key authentication, host-key verification, key held as a Kestra Secret from Key Vault. |
| **M2M ingest** | Next.js Route Handlers under `app/api/billrun/*`, **service-token bearer auth** | The platform's first machine-to-machine path — three handlers: stage-complete, run status, distribution outcome. No session semantics (§4). |

**Where compute lives.** Phase 2 moved stages 2–6 off the app and onto the engine, and that boundary is structurally enforced: `tests/guardrails/billing-trial-bill-compute-boundary.test.ts` asserts the retired app-side compute services do not exist, that `insertTrial`/`deleteTrial`/`replaceForBill` are not exported, and that only `post-run.ts` calls `stampPosted`. Phase 3's recurring derivation and `customer_bill_line` writes therefore belong to the **flow**, not to `services/billing/**`.

**Cross-schema boundary.** `billing` ⇄ `rating` ⇄ `inventory`/`product`/`ordering` ⇄ `billing.document`/pgledger are joined by **plain-text keys — no cross-schema foreign keys in either direction**, so the deployables' migrations stay decoupled.

## 3. Storage model — database vs file vs cache

Per `architecture.md` §3, Postgres is the single system of record; the platform anticipates Azure Blob for "Bill Run invoice artifacts", emulated by Azurite locally. Module specifics:

| Store | What | Notes |
| --- | --- | --- |
| **Postgres — `billing` schema** | `bill_run`, `bill_run_account`, `bill_run_account_stage`, `customer_bill`, **`customer_bill_line`**, `customer_bill_tax_item`, `bill_run_invoices`, `bill_run_distribution`, `bill_template_version` | IDs = prefix + zero-padded per-table sequence; money is `numeric(18,2)` text-mode. |
| **Postgres — partitioned** | `bill_run_account`, `bill_run_account_stage`, `customer_bill`, **`customer_bill_line`**, `customer_bill_tax_item`, `bill_run_invoices`, `bill_run_distribution` — range-partitioned on `period_partition`, **84-partition (7-year)** detach-and-archive | Composite PK/unique keys include `period_partition`. `customer_bill_line` inherits its parent's 7-year policy — a line is part of the invoice's statutory record and must neither outlive nor predecease its header. `bill_run` (header) and `bill_template_version` (catalog) are not partitioned. |
| **Postgres — `rating` schema (external)** | `rating.udr_rated` — real, populated by the rating engine | Bill Run holds `SELECT` on `rating.*` plus **column-scoped `UPDATE` on exactly six columns**. **No `rating.udr_exception` exists** — uncharged items are `status = 'BILL_NOTUSED'`. |
| **Postgres — read-only cross-schema** | `inventory.product_inventory`, `product.product_offering`, `product.product_offering_price`, `ordering.order_item_price_override`, `billing.billing_account`, `billing.bill_cycle` | Enumerated per table for `billrun_runtime`, never `ON ALL TABLES`. The correlation and recurring-pricing inputs. |
| **File storage — Azure Blob** | `invoices/` container: `{YYYY-MM}/{INV-number}.pdf` (immutable, checksummed, registered in `bill_run_invoices`) and `{YYYY-MM}/{bill_run_id}-report.csv` (transient distribution payload, **no** `bill_run_output` row) | **The distribution flow reads this store directly** by `blob_ref`; the app does not proxy artifacts. Azurite locally. |
| **File storage — SFTP (egress only)** | `{remote_base}/invoices/{YYYY-MM}/{INV}.pdf`, `{remote_base}/reports/{YYYY-MM}/{bill_run_id}-report.csv` | Delivery destination, not a store the app reads back. Separate subtrees because the two artifacts have different audiences (§4). |
| **Cache** | **None** | Run status and pre-approval totals are derived live and never cached. The **immutable run total is the `bill_run.total_amount` stamp written once at `APPROVED`**; from `APPROVED` onward it is read back from that stamp, not re-derived. |

**Charge integrity — the model that replaced "no billing-side copy".** `customer_bill_line` stores what the customer is billed, at `(product_offering_id, udr_type)` grain, with `gross_amount` / `discount_amount` / `net_amount` and — for derived recurring lines — the resolved price snapshot (price ref, rate, quantity, effective date). `customer_bill.subtotal` equals `SUM(net_amount)`. `charge_checksum` is computed over the line **content** (`source`, `ref_product_offering_id`, `udr_type`, `line_type`, `gross_amount`, `discount_amount`, `net_amount`), ordered deterministically, so it is reproducible from an archived invoice rather than only from the same database rows. All three money columns are hashed (not `net_amount` alone) so a discount that preserves the net is still tamper-evident once discounting lands. `rating.udr_rated` remains the per-record drill-down, reconciled against the lines by `udr_count` and the stored grouping key.

**Why the snapshot is mandatory, and authoritative on rerun.** `product.product_offering_price` is start-dated with the end bound derived by a `lead()` window, so as-of pricing resolves correctly on first derivation. The re-pricing hazard is the **catalog** price itself: a price row inserted later with an earlier `start_date_time` shifts the `lead()` window, so re-resolving on a rerun would silently re-price a period a human already reviewed. (`ordering.order_item_price_override` is insert-only and cannot change, so it is not the hazard.) Therefore the flow **reads the stored snapshot on rerun rather than re-resolving**; as-of resolution runs only when no prior snapshot exists.

## 4. Authentication, authorization & data ownership

**Three authentication paths.**

- **Human (UI + Server Actions):** unchanged from the platform — Better-Auth DB-backed session, live status + effective permissions resolved per request. No authz state in the session.
- **Machine, inbound (engine → app):** `app/api/billrun/*` has **no session semantics**. A dedicated bearer service token (constant-time compare, never logged, Zod-validated, HTTPS-only). Stage signals are rejected unless the run is `PROCESSING`; distribution outcomes unless it is `DISTRIBUTING`.
- **Machine, outbound (app → engine, engine → blob, engine → SFTP):** three independent credentials, one per direction and destination. App→engine is Kestra-OSS instance-wide Basic Auth from Key Vault. Engine→blob is the worker's own managed identity or connection string. Engine→SFTP is an **SSH private key** held as a Kestra Secret from Key Vault, with host-key verification enabled. No credential is ever literal in a flow YAML.

**Authorization — three module permissions**, unchanged:

| Permission | Grants | Implies |
| --- | --- | --- |
| `billrun_view` | list, drill-down, CSV export | — |
| `billrun_operate` | trigger, rerun, cancel, start/rerun distribution | `billrun_view` |
| `billrun_approve` | reject, approve + post (the money gate) | `billrun_view` |

**Four-eyes (segregation of duties):** the user who triggered the **final** attempt can never approve/post the run — enforced in the service layer, not the UI. Because INV auto-posts, run-level four-eyes is the **sole** second signature on the ledger.

**Data ownership — two writers in `billing`, one sanctioned writer in `rating`.**

| Writer | May write | Must NOT write |
| --- | --- | --- |
| **App** (`app_runtime`) | `bill_run`, `bill_run_account`, `bill_run_account_stage`, `bill_run_invoices`, `bill_run_distribution`, `billing.document`/pgledger (posting), the `customer_bill` posting stamps; and the **four** abandon/gate `udr_rated` transitions (approve, reject, cancel, rerun-release) | Trial bill data — `customer_bill` rows, `customer_bill_line`, `customer_bill_tax_item` — beyond the posting stamps. It holds **`SELECT`-only** on `customer_bill_line` (for the posting checksum and the final render) and no DML on it at all. |
| **Engine** (`billrun_runtime`) | `customer_bill`, `customer_bill_line`, `customer_bill_tax_item`, and the six claim columns on `rating.udr_rated` (`RATED → BILL_DRAFT` only) | `bill_run`, `bill_run_account`, `bill_run_account_stage`, `billing.document`, pgledger, `bill_run_invoices`. It holds **no table-level `DELETE`** on `customer_bill_line` — re-derivation deletes only through the scoped `SECURITY DEFINER` `billrun_delete_trial_bill` (Inv #16), so a direct grant would be both redundant and a way around that function's `ref_inv_document_id IS NULL` scoping. |
| **Rating** (`rating_runtime`) | `rating.*` (INSERT + `status` UPDATE) | Any `billing` write (explicit `REVOKE`); and, from this phase, any `status` transition **out of** `BILL_DRAFT`/`BILL_APPROVED` |

The app's `rating` write surface is **one file** — `db/repositories/billing/udr-status.repository.ts` — enforced by `tests/guardrails/billing-rating-write-boundary.test.ts`, limited to the six claim columns with no INSERT. The **claim itself is the flow's**, not the app's: the app only ever moves a row *out* of a claim — approve → `BILL_APPROVED`, and reject / cancel / **rerun** → release to `RATED` (Inv #19). Because the flow claims `RATED` only, the app's release is what makes a second attempt possible at all.

**Artifact disclosure boundary.** The per-run report CSV is an **invoice register** listing every account, invoice number and amount in the run. It is safe on the single internal SFTP destination in scope here. **Any future per-customer or customer-facing target must be invoice-only** — a property of the target, recorded alongside `is_mandatory` in the app-owned target definition, not a convention.

## 5. Background tasks & AI

Consistent with `architecture.md` §6: **no AI/ML**, and **the application itself runs no schedulers, cron jobs, or background workers.**

| Mechanism | Where it runs | Why it's not an app job |
| --- | --- | --- |
| **Run materialization** | Per page load (lazy, `ON CONFLICT DO NOTHING`) | A run "exists on the 1st" because any view on/after the 1st creates it. |
| **`STALLED` detection** | Derived on read | Shown when the run is `PROCESSING`/`DISTRIBUTING` and `last_progress_at` exceeds the threshold; nothing writes a stalled row. Every stage signal **and every distribution outcome** bumps the heartbeat, so a long delivery is never falsely flagged. |
| **Pipeline orchestration and transport** | **External workflow engine (Kestra)** | A separate deployable. It signals the app over M2M and cannot bypass app authorization because it is not in the app. |
| **Distribution retry** | **In-execution, once**, then reported `FAILED` | The flow retries an upload once; beyond that, recovery is operator-triggered (`rerunDistribution` re-triggers only the prior round's failed artifacts). The app has no scheduler to drive automatic backoff. |
| **Partition maintenance** | **`pg_cron` (DB-level)** via `pg_partman` | A database scheduler, not app code. Premake + detach-and-archive only. |

No email/SMTP. Distribution is SFTP only.

## 6. Module invariants

Rules this module must never violate, **in addition to** the platform invariants in `architecture.md` §7. Platform **Invariant #18** (financially significant rows are immutable; corrections insert a successor) applies directly. Each is testable; **[CRITICAL]** marks those whose violation silently corrupts financial data.

1. **The bill run never rates usage.** It collects already-rated `rating.udr_rated` records; no usage-rating logic exists in `billing`. Deriving a recurring charge from a subscription and an as-of catalog price is **billing**, not rating — the distinction is that rating consumes a delivered usage file and the bill run does not.
2. **Six claim columns, no other cross-schema writes, no cross-schema FKs.** The only columns the app or the engine writes in `rating` are `status`, `billrun_ref_id`, `billrun_ban_id`, `billrun_attempt`, `billrun_checksum`, `upsert_datetime`. No `INSERT`, no `DELETE`, no other column. Schemas join on plain-text keys.
3. **[CRITICAL] `customer_bill_line` is the bill's charge record, and `charge_checksum` is anchored on it.** *(Replaces the former "no billing-side charge copy".)* The checksum hashes line **content**, never surrogate ids, so it is reproducible from an archived invoice — and it hashes **all three money columns** (`gross_amount`, `discount_amount`, `net_amount`), not `net_amount` alone, so a discount that preserves the net is still tamper-evident once discounting lands. `customer_bill.subtotal` must equal `SUM(customer_bill_line.net_amount)`.
4. **[CRITICAL] `ref_inv_document_id` is the finalization boundary.** A `customer_bill` with it set is never UPDATEd, DELETEd, or stage-invalidated — **DB-enforced on the header** by `customer_bill_finalization_guard` (migration `0033`). Its `customer_bill_line` rows are protected by app-layer discipline (rerun/reject only ever touch unfinalized bills, via the `ref_inv_document_id IS NULL`-scoped `billrun_delete_trial_bill`) plus the `charge_checksum`; there is **no** finalization trigger on the child table, and the checksum is computed once at posting and not re-verified afterward. Posting resumes by skipping finalized accounts. *(Eng review 2026-09-14: the child-line immutability is app-layer + checksum, not a DB trigger — a deliberate choice; see the review report.)*
5. **[CRITICAL] Idempotency is a database constraint, never the orchestrator.** `UNIQUE (ref_bill_run_id, ref_billing_account_id, stage, attempt, period_partition)` on `bill_run_account_stage`, and `(run, target, artifact_ref, distribution_attempt, period_partition)` on `bill_run_distribution`, inserted first inside the handler's transaction. The engine provides no server-side dedup.
6. **[CRITICAL] Posting is per-account, in its own transaction, resumable, and never double-posts.** An account already carrying `ref_inv_document_id` is skipped on retry; `postDocument` runs inside the caller's transaction so a crash rolls INV + ledger + stamp back together.
7. **Invoice numbers are consumed only on successful posting.** A trial or `SKIPPED` account reserves none; a rollback may leave a rare gap — tolerated.
8. **Four-eyes on the money gate.** The final-attempt trigger actor can never approve/post the run; enforced in the service layer.
9. **M2M ingest has no session semantics.** `app/api/billrun/*` never calls `getSession`; it authenticates a bearer service token and rejects any signal whose run is in the wrong state.
10. **The app runs no schedulers or background jobs.** Runs materialize lazily; `STALLED` is derived on read; the engine and `pg_cron` are the only schedulers.
11. **`period_partition` is fixed per run, not insert-time.** Every row for a run — including a cross-month rerun — lands in that run's period partition. Composite PK/unique keys include it.
12. **Run status is recomputed under a row lock, never an incremental counter.** `SELECT … FOR UPDATE` on `bill_run`; account-grain truth is `bill_run_account`/`bill_run_account_stage`; any cached counter must equal the derived value. Distribution status is derived the same way, from `bill_run_distribution` — never forced.
13. **`gl_event_at` is fixed at trigger and defines the GL period.** Revenue posts to the run-month GL period, which the Accounts period-close guard keeps open until the run is `COMPLETED`/`CANCELLED`.
14. **[CRITICAL] Rating rows for an approved run are immutable and retained.** The rating subsystem may not purge or overwrite a run's charge rows once the run is `APPROVED`; posted rows are permanently immutable for the invoice's statutory life.
15. **RETIRED (phase 3, D31) — "Stub-data mode is unmissable and isolated."** `BILLRUN_PLACEHOLDER_MODE` and its `PlaceholderBanner`/`PlaceholderBadge` are removed: once the real processing and distribution flows deploy, the banner's claim that "the billing steps are placeholders" is false, and a loud warning that is wrong is worse than none. **The number is kept as a tombstone, not reused**, so every existing citation of Inv #15 resolves to an explanation rather than to an unrelated rule. What does *not* retire with it: the `_SAMPLE_` provenance marking on seeded `udr_rated` rows, the prod guard on `db:seed-sample`, and its absence from `db:setup` — those are seed-integrity rules independent of any badge, and they matter more in phase 3, not less (Inv #12 of the seed guardrails; code-standards §9 items 8 and 16).

**Added this phase:**

16. **[CRITICAL] Every charge line declares its source, and each source carries its own exactly-once mechanism.** `USAGE` is guaranteed by the claim (`billrun_ref_id` stamp + the live-row unique constraint); `RECURRING` by the period being the key (one run per cycle per period) — and, because `RECURRING` has no row-grain marker, by re-derivation being a **whole-account line replace** (delete all of an account's `customer_bill_line` via `billrun_delete_trial_bill`, then re-insert; never a per-line upsert), so a subscription yields exactly one recurring line per `(run, account)`; `OCC` — reserved, not built — by a billed marker set at posting on an origination-domain occurrence ledger. **`customer_bill_line` is never itself an occurrence ledger:** it is per-run and rerun-destructible, so nothing whose billed-exactly-once evidence must survive a rerun may be stored only there. This last boundary is prose-only today (the `source='OCC'` enum value is reserved without a structural guard); a `CHECK`/trigger is added when OCC is built, or the enum value is deferred until then.
17. **[CRITICAL] No app code computes or writes trial bill data.** All bill-data computation is the engine's, as `billrun_runtime`. The app's only `customer_bill` write is the posting stamp. Structurally enforced by `billing-trial-bill-compute-boundary.test.ts`.
18. **[CRITICAL] Rating may not supersede a claimed row.** A batch colliding with any live **claimed** row (`BILL_DRAFT` or `BILL_APPROVED`) is refused whole. Enforced by the `rating.rating_status_guard` trigger, not only by the loader's pre-check — a plain `SELECT` guard loses the race between the check and the supersede `UPDATE`. The operational consequence: **reject or cancel an open run before reloading a corrected file.**
19. **[CRITICAL] A claim is released whenever its attempt is abandoned — by reject, by cancel, and by rerun.** All three return the rows to `RATED` with all four claim columns cleared; the `REJECTED_PENDING_REPROCESS` stage marker is the sole reject signal the approval gate reads. Two consequences, and both are why this is one rule rather than three: a released row is *live*, so the rating engine's supersede sweep can retire it normally (a parked, not-live row would be skipped and survive as an orphan); and since Collection claims `RATED` only, any row left at `BILL_DRAFT` from an abandoned attempt is **unclaimable by the next attempt and silently under-bills**. Release must therefore happen **before** the re-trigger, never after.
20. **Derived recurring charges snapshot their price onto the line, and the snapshot is authoritative on rerun.** The resolved price ref, rate, quantity and effective date are stored, and a rerun **reads the snapshot rather than re-resolving**; as-of resolution runs only when no prior snapshot exists. The hazard the snapshot defeats is the **catalog price**: a `product_offering_price` row inserted later with an earlier start shifts the `lead()` window, so re-resolving would silently re-price a period a human already reviewed. `ordering.order_item_price_override` is insert-only and cannot change, so it is *not* the hazard — an earlier framing of this rule said otherwise and was wrong.
21. **Line numbering is deterministic.** `line_no` is assigned by ordering the grouping key, not by insertion order, so a re-derived or re-issued invoice keeps its numbering and a future credit note can reference a line safely.
22. **"Uncharged" means no charge line, not no usage.** An account is Uncharged when it produced no `customer_bill_line` (or its lines net to zero) — not when it is absent from `rating.udr_rated`. A recurring-only account with zero usage is **billed**. `udr_rated.status = 'BILL_NOTUSED'` is a separate per-record exception surface.
23. **The engine's cross-schema reads are enumerated per table.** `billrun_runtime` never receives `ON ALL TABLES` and never receives `ALTER DEFAULT PRIVILEGES`; a new read requirement is a reviewed one-line grant. The same rule governs `app_runtime` inside `billing`: its grants are per-table too, so a new billing table is **inaccessible to the app until explicitly granted** — `customer_bill_line` needed an explicit `SELECT` for the posting checksum and the render (§4).
24. **The subscriber→account correlation is computed once per account and shared.** Validation (stage 2) cannot assert currency or window coverage until it knows *which* `udr_rated` rows belong to the account, and that is only known after the correlation Collection (stage 3) performs. The correlation runs once — Validation asserts against the correlated set, or its assertions fold into the claim step — so the heaviest join in the pipeline is never run twice per account.
25. **An unresolvable subscriber is a surfaced, non-blocking per-record exception (D32).** A `udr_rated` row whose `udr_subscriber_ref_id` resolves to no `product_inventory` row is left at `RATED`, unclaimed and untouched, and surfaced alongside `BILL_NOTUSED` on the per-record exception surface; the run continues and the count is informational on the pre-approval checklist. It is **never** silently dropped — unlike rating's `LOOKUP_MISS`, the row here is already a rated charge with an amount, so dropping it is revenue leakage. It is **not** an account-grain failure either: not knowing the account is the failure, so there is nothing to attach one to. Because the row stays claimable, the next run bills it flagged prior-period once the inventory is fixed.
26. **An account excluded at scoping forgoes the whole month, both sources.** A partial-period account (mid-period start, cease or suspend) is `EXCLUDED` before the flow runs, so it bills neither recurring nor usage for that period and resumes at the next full cycle. This is the cost of deferring proration and must be stated as a revenue rule, not discovered. It is also why "`EXCLUDED`" and "Uncharged" (Inv #22) are different things: an excluded account never reaches the stage that would produce a charge line.
27. **A distribution failure never reverses or blocks a posted `INV`,** and a run parked in distribution never blocks the next cycle — operability keys off `INVOICED`, not `COMPLETED`. **Completion is per `(target, artifact_ref)` and scales with the number of mandatory targets:** the expected mandatory-artifact count is the artifact count **multiplied by** the mandatory-target count, and latest-outcome dedup keys on `(target, artifact_ref)` — never on the artifact alone. A count that assumes a single target silently marks a run `COMPLETED` when one target has delivered and another has not. *(Held #15 until phase 3; moved so #15 could become the retirement tombstone above without reusing a cited number.)*
28. **[CRITICAL] An unresolvable or `tiered` recurring price fails its account HARD (D33).** No as-of `recurring` price, or a `pricing_model = 'tiered'` row (unratable by the flat resolver — `amount IS NULL` by CHECK), sends the account to `PROCESSING_FAILED` with a `HARD` finding and `RECURRING_PRICE_NOT_FOUND` or `RECURRING_PRICE_UNSUPPORTED`; no bill is produced for it until the catalog is fixed and it is rerun. This blocks where Inv #25 does not, because a skipped recurring charge is **not recoverable**: recurring is period-keyed, next month's run bills next month, and the catch-up machinery for a missed period is the unbuilt OCC ledger. An invoice issued short would never be corrected.
