## 3. Storage model — database vs file vs cache

Per `architecture.md` §3, Postgres is the single system of record; the platform anticipates Azure Blob for "Bill Run invoice artifacts", emulated by Azurite locally. Module specifics:

| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Charge integrity — the model that replaced "no billing-side copy".** `customer_bill_line` stores what the customer is billed, at `(product_offering_id, udr_type)` grain, with `gross_amount` / `discount_amount` / `net_amount` and — for derived recurring lines — the resolved price snapshot (price ref, rate, quantity, effective date). `customer_bill.subtotal` equals `SUM(net_amount)`. `charge_checksum` is computed over the line **content** (`source`, `ref_product_offering_id`, `udr_type`, `line_type`, `gross_amount`, `discount_amount`, `net_amount`), ordered deterministically, so it is reproducible from an archived invoice rather than only from the same database rows. All three money columns are hashed (not `net_amount` alone) so a discount that preserves the net is still tamper-evident once discounting lands. `rating.udr_rated` remains the per-record drill-down, reconciled against the lines by `udr_count` and the stored grouping key.

**Why the snapshot is mandatory, and authoritative on rerun.** `product.product_offering_price` is start-dated with the end bound derived by a `lead()` window, so as-of pricing resolves correctly on first derivation. The re-pricing hazard is the **catalog** price itself: a price row inserted later with an earlier `start_date_time` shifts the `lead()` window, so re-resolving on a rerun would silently re-price a period a human already reviewed. (`ordering.order_item_price_override` is insert-only and cannot change, so it is not the hazard.) Therefore the flow **reads the stored snapshot on rerun rather than re-resolving**; as-of resolution runs only when no prior snapshot exists.

## 4. Authentication, authorization & data ownership

**Three authentication paths.**

- **Human (UI + Server Actions):** unchanged from the platform — Better-Auth DB-backed session, live status + effective permissions resolved per request. No authz state in the session.
- **Machine, inbound (engine → app):** `app/api/billrun/*` has **no session semantics**. A dedicated bearer service token (constant-time compare, never logged, Zod-validated, HTTPS-only). Stage signals are rejected unless the run is `PROCESSING`; distribution outcomes unless it is `DISTRIBUTING`.
- **Machine, outbound (app → engine, engine → blob, engine → SFTP):** three independent credentials, one per direction and destination. App→engine is Kestra-OSS instance-wide Basic Auth from Key Vault. Engine→blob is the worker's own managed identity or connection string. Engine→SFTP is an **SSH private key** held as a Kestra Secret from Key Vault, with host-key verification enabled. No credential is ever literal in a flow YAML.

**Authorization — three module permissions**, unchanged:

| Permission        | Grants                                           | Implies        |
| ----------------- | ------------------------------------------------ | -------------- |

## 6. Module invariants

Rules this module must never violate, **in addition to** the platform invariants in `architecture.md` §7. Platform **Invariant #18** (financially significant rows are immutable; corrections insert a successor) applies directly. Each is testable; **[CRITICAL]** marks those whose violation silently corrupts financial data.

1. **The bill run never rates usage.** It collects already-rated `rating.udr_rated` records; no usage-rating logic exists in `billing`. Deriving a recurring charge from a subscription and an as-of catalog price is **billing**, not rating — the distinction is that rating consumes a delivered usage file and the bill run does not.
2. **Six claim columns, no other cross-schema writes, no cross-schema FKs.** The only columns the app or the engine writes in `rating` are `status`, `billrun_ref_id`, `billrun_ban_id`, `billrun_attempt`, `billrun_checksum`, `upsert_datetime`. No `INSERT`, no `DELETE`, no other column. Schemas join on plain-text keys.
3. **[CRITICAL] `customer_bill_line` is the bill's charge record, and `charge_checksum` is anchored on it.** _(Replaces the former "no billing-side charge copy".)_ The checksum hashes line **content**, never surrogate ids, so it is reproducible from an archived invoice — and it hashes **all three money columns** (`gross_amount`, `discount_amount`, `net_amount`), not `net_amount` alone, so a discount that preserves the net is still tamper-evident once discounting lands. `customer_bill.subtotal` must equal `SUM(customer_bill_line.net_amount)`.
4. **[CRITICAL] `ref_inv_document_id` is the finalization boundary.** A `customer_bill` with it set is never UPDATEd, DELETEd, or stage-invalidated — **DB-enforced on the header** by `customer_bill_finalization_guard` (migration `0033`). Its `customer_bill_line` rows are protected by app-layer discipline (rerun/reject only ever touch unfinalized bills, via the `ref_inv_document_id IS NULL`-scoped `billrun_delete_trial_bill`) plus the `charge_checksum`; there is **no** finalization trigger on the child table, and the checksum is computed once at posting and not re-verified afterward. Posting resumes by skipping finalized accounts. _(Eng review 2026-09-14: the child-line immutability is app-layer + checksum, not a DB trigger — a deliberate choice; see the review report.)_
5. **[CRITICAL] Idempotency is a database constraint, never the orchestrator.** `UNIQUE (ref_bill_run_id, ref_billing_account_id, stage, attempt, period_partition)` on `bill_run_account_stage`, and `(run, target, artifact_ref, distribution_attempt, period_partition)` on `bill_run_distribution`, inserted first inside the handler's transaction. The engine provides no server-side dedup.
6. **[CRITICAL] Posting is per-account, in its own transaction, resumable, and never double-posts.** An account already carrying `ref_inv_document_id` is skipped on retry; `postDocument` runs inside the caller's transaction so a crash rolls INV + ledger + stamp back together.
7. **Invoice numbers are consumed only on successful posting.** A trial or `SKIPPED` account reserves none; a rollback may leave a rare gap — tolerated.
8. **Four-eyes on the money gate.** The final-attempt trigger actor can never approve/post the run; enforced in the service layer.
9. **M2M ingest has no session semantics.** `app/api/billrun/*` never calls `getSession`; it authenticates a bearer service token and rejects any signal whose run is in the wrong state.
10. **The app runs no schedulers or background jobs.** Runs materialize lazily; `STALLED` is derived on read; the engine and `pg_cron` are the only schedulers.
11. **`period_partition` is fixed per run, not insert-time.** Every row for a run — including a cross-month rerun — lands in that run's period partition. Composite PK/unique keys include it.
12. **Run status is recomputed under a row lock, never an incremental counter.** `SELECT … FOR UPDATE` on `bill_run`; account-grain truth is `bill_run_account`/`bill_run_account_stage`; any cached counter must equal the derived value. Distribution status is derived the same way, from `bill_run_distribution` — never forced.
13. **`gl_event_at` is fixed at trigger and defines the GL period.** Revenue posts to the run-month GL period, which the Accounts period-close guard keeps open until the run is `COMPLETED`/`CANCELLED`.
14. **[CRITICAL] Rating rows for an approved run are immutable and retained.** The rating subsystem may not purge or overwrite a run's charge rows once the run is `APPROVED`; posted rows are permanently immutable for the invoice's statutory life.
15. **RETIRED (phase 3, D31) — "Stub-data mode is unmissable and isolated."** `BILLRUN_PLACEHOLDER_MODE` and its `PlaceholderBanner`/`PlaceholderBadge` are removed: once the real processing and distribution flows deploy, the banner's claim that "the billing steps are placeholders" is false, and a loud warning that is wrong is worse than none. **The number is kept as a tombstone, not reused**, so every existing citation of Inv #15 resolves to an explanation rather than to an unrelated rule. What does _not_ retire with it: the `_SAMPLE_` provenance marking on seeded `udr_rated` rows, the prod guard on `db:seed-sample`, and its absence from `db:setup` — those are seed-integrity rules independent of any badge, and they matter more in phase 3, not less (Inv #12 of the seed guardrails; code-standards §9 items 8 and 16).

**Added this phase:**

16. **[CRITICAL] Every charge line declares its source, and each source carries its own exactly-once mechanism.** `USAGE` is guaranteed by the claim (`billrun_ref_id` stamp + the live-row unique constraint); `RECURRING` by the period being the key (one run per cycle per period) — and, because `RECURRING` has no row-grain marker, by re-derivation being a **whole-account line replace** (delete all of an account's `customer_bill_line` via `billrun_delete_trial_bill`, then re-insert; never a per-line upsert), so a subscription yields exactly one recurring line per `(run, account)`; `OCC` — reserved, not built — by a billed marker set at posting on an origination-domain occurrence ledger. **`customer_bill_line` is never itself an occurrence ledger:** it is per-run and rerun-destructible, so nothing whose billed-exactly-once evidence must survive a rerun may be stored only there. This last boundary is prose-only today (the `source='OCC'` enum value is reserved without a structural guard); a `CHECK`/trigger is added when OCC is built, or the enum value is deferred until then.
17. **[CRITICAL] No app code computes or writes trial bill data.** All bill-data computation is the engine's, as `billrun_runtime`. The app's only `customer_bill` write is the posting stamp. Structurally enforced by `billing-trial-bill-compute-boundary.test.ts`.
18. **[CRITICAL] Rating may not supersede a claimed row.** A batch colliding with any live **claimed** row (`BILL_DRAFT` or `BILL_APPROVED`) is refused whole. Enforced by the `rating.rating_status_guard` trigger, not only by the loader's pre-check — a plain `SELECT` guard loses the race between the check and the supersede `UPDATE`. The operational consequence: **reject or cancel an open run before reloading a corrected file.**
19. **[CRITICAL] A claim is released whenever its attempt is abandoned — by reject, by cancel, and by rerun.** All three return the rows to `RATED` with all four claim columns cleared; the `REJECTED_PENDING_REPROCESS` stage marker is the sole reject signal the approval gate reads. Two consequences, and both are why this is one rule rather than three: a released row is _live_, so the rating engine's supersede sweep can retire it normally (a parked, not-live row would be skipped and survive as an orphan); and since Collection claims `RATED` only, any row left at `BILL_DRAFT` from an abandoned attempt is **unclaimable by the next attempt and silently under-bills**. Release must therefore happen **before** the re-trigger, never after.
20. **Derived recurring charges snapshot their price onto the line, and the snapshot is authoritative on rerun.** The resolved price ref, rate, quantity and effective date are stored, and a rerun **reads the snapshot rather than re-resolving**; as-of resolution runs only when no prior snapshot exists. The hazard the snapshot defeats is the **catalog price**: a `product_offering_price` row inserted later with an earlier start shifts the `lead()` window, so re-resolving would silently re-price a period a human already reviewed. `ordering.order_item_price_override` is insert-only and cannot change, so it is _not_ the hazard — an earlier framing of this rule said otherwise and was wrong.
21. **Line numbering is deterministic.** `line_no` is assigned by ordering the grouping key, not by insertion order, so a re-derived or re-issued invoice keeps its numbering and a future credit note can reference a line safely.
22. **"Uncharged" means no charge line, not no usage.** An account is Uncharged when it produced no `customer_bill_line` (or its lines net to zero) — not when it is absent from `rating.udr_rated`. A recurring-only account with zero usage is **billed**. `udr_rated.status = 'BILL_NOTUSED'` is a separate per-record exception surface.
23. **The engine's cross-schema reads are enumerated per table.** `billrun_runtime` never receives `ON ALL TABLES` and never receives `ALTER DEFAULT PRIVILEGES`; a new read requirement is a reviewed one-line grant. The same rule governs `app_runtime` inside `billing`: its grants are per-table too, so a new billing table is **inaccessible to the app until explicitly granted** — `customer_bill_line` needed an explicit `SELECT` for the posting checksum and the render (§4).
24. **The subscriber→account correlation is computed once per account and shared.** Validation (stage 2) cannot assert currency or window coverage until it knows _which_ `udr_rated` rows belong to the account, and that is only known after the correlation Collection (stage 3) performs. The correlation runs once — Validation asserts against the correlated set, or its assertions fold into the claim step — so the heaviest join in the pipeline is never run twice per account.
25. **An unresolvable subscriber is a surfaced, non-blocking per-record exception (D32).** A `udr_rated` row whose `udr_subscription_ref_id` resolves to no `product_inventory` row is left at `RATED`, unclaimed and untouched, and surfaced alongside `BILL_NOTUSED` on the per-record exception surface; the run continues and the count is informational on the pre-approval checklist. It is **never** silently dropped — unlike rating's `LOOKUP_MISS`, the row here is already a rated charge with an amount, so dropping it is revenue leakage. It is **not** an account-grain failure either: not knowing the account is the failure, so there is nothing to attach one to. Because the row stays claimable, the next run bills it flagged prior-period once the inventory is fixed.
26. **An account excluded at scoping forgoes the whole month, both sources.** A partial-period account (mid-period start, cease or suspend) is `EXCLUDED` before the flow runs, so it bills neither recurring nor usage for that period and resumes at the next full cycle. This is the cost of deferring proration and must be stated as a revenue rule, not discovered. It is also why "`EXCLUDED`" and "Uncharged" (Inv #22) are different things: an excluded account never reaches the stage that would produce a charge line.
27. **A distribution failure never reverses or blocks a posted `INV`,** and a run parked in distribution never blocks the next cycle — operability keys off `INVOICED`, not `COMPLETED`. **Completion is per `(target, artifact_ref)` and scales with the number of mandatory targets:** the expected mandatory-artifact count is the artifact count **multiplied by** the mandatory-target count, and latest-outcome dedup keys on `(target, artifact_ref)` — never on the artifact alone. A count that assumes a single target silently marks a run `COMPLETED` when one target has delivered and another has not. _(Held #15 until phase 3; moved so #15 could become the retirement tombstone above without reusing a cited number.)_
28. **[CRITICAL] An unresolvable or `tiered` recurring price fails its account HARD (D33).** No as-of `recurring` price, or a `pricing_model = 'tiered'` row (unratable by the flat resolver — `amount IS NULL` by CHECK), sends the account to `PROCESSING_FAILED` with a `HARD` finding and `RECURRING_PRICE_NOT_FOUND` or `RECURRING_PRICE_UNSUPPORTED`; no bill is produced for it until the catalog is fixed and it is rerun. This blocks where Inv #25 does not, because a skipped recurring charge is **not recoverable**: recurring is period-keyed, next month's run bills next month, and the catch-up machinery for a missed period is the unbuilt OCC ledger. An invoice issued short would never be corrected.

**Added — Target Capacity Pricing update (2026-10-04):**

29. **[CRITICAL] Capacity pricing computes and writes in one transaction; Model 1 is billed, Model 2 only checks.** All capacity arithmetic is inline SQL CTEs in the `aggregation` step's per-account whole-account-replace transaction — no DB function, no Python, no second service (TC8). The billed figure is **Model 1** (`gross = Σ udr_rated_price + topUp`, anchored on the rated rows); the independent **Model-2** recompute (`max(Q, target) × baseRate`) in `verification` is a reconciliation check, never an alternate charge.
30. **[CRITICAL] A capacity rate mismatch is loud by default and never silently billed.** `CAPACITY_RATE_MATCHING` defaults **ON**: a per-row or Model-2 disagreement HARD-fails the account (`CAPACITY_RATE_MISMATCH`) with a diagnostic naming both rates and both version sources. Set OFF (a deliberate ops override), it must still **log a WARN, bill Model 1, and record the flag state on the run** — never a silent pass.
31. **Capacity components resolve off the subscription's pinned offering version, never the current ACTIVE.** The base `usage_rate` + the `capacity_commitment`/`capacity_motivation` components are read from the `product_offering_id` the subscription is pinned to (via `product_inventory → order_item`) — the same version rating priced from — so a grandfathered account is never mispriced against a newer ACTIVE version.
32. **A capacity offering is detected by its components, never by a column, and self-guards at account grain.** Identification is the presence of a `capacity_commitment`/`capacity_motivation` component; six HARD guards (`CAPACITY_MULTIPLE_SUBSCRIPTIONS`, `_BASE_RATE_NOT_FOUND`, `_UDR_TYPE_MISMATCH`, `_RATE_MISMATCH`, `_MULTI_STEP_UNSUPPORTED`, `_CURRENCY_MISMATCH`) fail only the offending account (`PROCESSING_FAILED`, rerunnable) while siblings bill. Correctness never depends on the prerequisite catalog column.
33. **The capacity line is generated from the subscription even at zero usage, at `(offering, unit_of_measure)` grain.** The commitment floor exists for the no-usage case, so the line is driven by the active subscription (like RECURRING), not by the presence of rated rows; `source='USAGE'`, `udr_type` = the spec `udrType`, `grouping_key = <offering>:CAPACITY:<unit>`.
34. **[CRITICAL] Each monetary component is rounded once; `gross` and `net` are derived, never re-rounded.** The top-up and each band amount round once (2 dp, HALF_UP); `gross = rated_amount + topUp` and `net = gross − discount` derive from the rounded parts, so the verification identities hold with no ±0.01 tolerance.
35. **[CRITICAL] The posting checksum appends `rated_amount`; `additional_info` is never hashed.** `charge_checksum` adds `rated_amount` as the **last** tuple element — appended, not inserted mid-tuple — so existing lines' serialization is unchanged; the `additional_info` calc trace is bound to the hashed columns by verification and is itself never hashed. _(Extends Inv #3.)_
36. **The capacity calculation trace is database-only; only the per-polygon usage appendix renders.** `additional_info` (pricing inputs, `calc`, `summary`) is never shown in the UI or on the invoice. The invoice renders a separate per-polygon usage appendix whose state/district come from the `productCardLookUp` ratecard **as matched at rating time and persisted onto `rating.udr_rated.state/district` (bm48, R9)**. The bill run and the render never join the ratecard for geo; rows rated before bm48 carry `NULL` geo and are shown, not dropped. Per-polygon only (no district summarisation), bounded to **≤ 10,000 rows/account**. _(Amended by bm48, 2026-10-08 — was "…come from the `productCardLookUp` ratecard, never from `udr_rated`". X1 closed as R9. The bm45 `additional_info.appendix` snapshot is still written by the flow; bm49 stops reading it.)_
37. **One capacity subscription per `(customer, product)`.** A customer holds at most one subscription of a given capacity offering (the rating resolver's `singleSubInstPerCust`); the per-account `CAPACITY_MULTIPLE_SUBSCRIPTIONS` guard is a redundant backstop. Multiple billing accounts per customer for the same capacity product is **not supported this phase**.
38. **Flow SQL is tested from the extracted YAML, and logic-green is not run-green.** DB suites run the SQL **extracted from `bill_run_processing.yml`** (never a hand-copied double — the double hid the PC14 break); and because the extraction strips Kestra pebble, a **live-Kestra execution** of the capacity path is a separate required gate (the module's historical defects were all pebble/execution-layer).

**Added — Invoice Template update (2026-10-07):**

39. **[CRITICAL] The invoice's charges come from `customer_bill_line`, and the bind reconciles before it renders.** The binder reads lines from `customer_bill_line` (all `ChargeSource` values: RECURRING, USAGE, OCC; `ONE_TIME` is open conflict code-standards C2 / bm47 gate G5 and is not a source until a spec defines its sourcing), tax from `customer_bill_tax_item`, the INV anchor from `billing.document`, and tax identity/address from `customer.organization` + `contact_medium` — aggregated on the fly, with **no new charge-copy table** (R1). `rating.udr_rated` is never a source of invoice **charges**; it feeds only the detailed usage section. Every bind asserts `Σ customer_bill_line.net_amount = customer_bill.subtotal`, and the CSV's line amounts must sum exactly to the bill; a mismatch is a render failure (Inv #40), never a rendered invoice.
40. **[CRITICAL] A render or validation failure parks the account; there is no legacy fallback.** The old `udr_rated`-based template is never used — not as a fallback, not behind a flag (R8). A failed final render is the existing **render-pending** state (bm19 D10: the INV stays posted, no `bill_run_invoices` row), surfaced on the run's exception surface and recovered through `retryRenderInvoice`; distribution's `unrenderedAccountIds` gate already refuses to complete around it. Parking is for data/validation/integrity failures only — "no template configured" cannot occur (Inv #42).
41. **[CRITICAL] Template, profile and CSV versions are stamped in the posting transaction, by the app only, in the same write as `ref_inv_document_id`.** `stampPosted` writes `ref_bill_format_id`, `ref_bill_template_version_id` (the **generated** version, which pins its layout), `ref_invoice_profile_version` and the CSV template version **together with** `ref_inv_document_id` — after that write `customer_bill_finalization_guard` (migration `0033`) rejects every UPDATE, so a stamp cannot be added or corrected later. The two reserved columns move from the engine's grant to the app's: `billrun_runtime`'s column-scoped `INSERT`/`UPDATE` on `ref_bill_format_id` / `ref_bill_template_version_id` (`billrun-db-roles.sql` Step 5) is **revoked**, and they join `ref_inv_document_id` / `posted_attempt` / `charge_checksum` as app-only posting stamps. **Built (bm54):** `postAccount` calls `resolveVersionsForPosting(tx)` (`services/billing/invoice-template/resolve-template.ts`) after `lockBillForPosting` and before `stampPosted`. It reads DB rows only (no blob read, no compile), with the same "current" precedence as a draft render: non-default ACTIVE ?? default, and the ACTIVE profile ?? `NULL` (G15 A). The catalog rows are read without a lock, so an activation during a run can give that run's accounts different versions. Each bill records exactly what it was posted under (known-issues §19).
42. **Template resolution is pinned → current ACTIVE → default, and a default always exists.** Final render, retry-render and any audit re-render use **only** the versions stamped on the bill; the draft (pro-forma) preview uses the current ACTIVE generated version + ACTIVE profile and persists nothing; the editor's preview of a **posted** bill uses that bill's pinned versions, not the current ACTIVE (R10). The seeded `INVTPL-STD-A4` layout and its default generated version carry `is_default = true`, are always ACTIVE, and can be neither retired nor deleted (R11). **Bills with NULL stamps (bm53):** every bill posted before bm54 has no stamps, so `resolveTemplate` resolves it to the immutable default (generated BTV00000002, CSV BTV00000003) with **no profile** (G15 A), never the current ACTIVE. The result is deterministic and identical to what was ACTIVE when it posted, because nothing is activatable before bm58. Resolution is never cached; the only cache is `load.ts`'s memo of verified, compiled templates keyed by version id (Inv #45).
43. **Reprint returns the stored PDF bytes; reproducibility is `charge_checksum`.** An issued invoice is never re-rendered for reprint — Chromium writes `/CreationDate`/`/ModDate`, so a re-render is not byte-identical (C1). Reproducibility is proven by recomputing the existing `customer_bill.charge_checksum` from the bill's lines, **not** by a rendered-HTML hash (§15 correction; the body's HTML-hash proposal is superseded).
44. **Template, asset and profile versions are append-only, write-once and retire-only.** `bill_template_version` and `bill_asset_version` rows are never UPDATEd beyond their status/activation/retirement stamps and never hard-deleted; status runs DRAFT → ACTIVE → RETIRED with **one ACTIVE per (`ref_bill_format_id`, `kind`)**, enforced by a partial unique index, not application code (the always-ACTIVE `is_default` row coexists because the one-ACTIVE index **excludes** the default — X3 resolved, bm50: `btv_one_active_uq … WHERE status = 'ACTIVE' AND NOT is_default`). Their blob objects are written with `writeOnce` (`if-none-match: *`). A DRAFT is never used to render an invoice. Retired versions are retained at least as long as any invoice references them (O10).
45. **[CRITICAL] Every stored template and logo is checksum-verified on every load.** `load(version)` verifies the blob against the stored checksum before `Handlebars.compile`; the logo is verified before it is inlined. A mismatch fails the render (Inv #40) — it never renders with a substitute.
46. **Admin input can never become template code.** Admins only toggle structure booleans; they never author markup. Handlebars runs with auto-escaping on, **triple-stash forbidden**, `knownHelpersOnly`, and no eval-style helpers. Generated `.hbs` contains only `{{ }}` placeholders — no `[[ ]]` generation directive survives generation. A CI layout lint rejects raw `<img src>` and any external URL; images enter only via `{{company.logoUrl}}` / `{{asset}}`.
47. **The render makes no network fetch and no ratecard query.** The logo is inlined as a data URI (so Playwright's `networkidle` is deterministic), and usage-section geo is a value already frozen before render — never looked up from `product.ratecard_ran_usage_lkp` at render time. (The frozen value lives on `rating.udr_rated.state/district`, captured at rating — X1 resolved as R9 by bm48.)
48. **Uploaded logos are validated and sanitized before they are stored.** PNG/JPEG/SVG only, ≤ 500 KB, ≥ 300 px, MIME checked against magic bytes; SVG has `<script>`, event handlers, `<foreignObject>` and external references stripped or rejected. Validation runs server-side in the action/service path, not only in the browser.
49. **Structure and activation rules are enforced server-side, and every save/activation is audited.** Mandatory sections cannot be hidden, activation requires a change note, and profile activation requires a logo — checked in the service, not only by locked checkboxes. Both screens require `invoice_settings` (READ to view, EDIT to save/activate); every save and activation writes `core.AUDIT_LOG`.
50. **"Amount due" is this invoice's current charges only, and tax is bill-level only.** No balance brought forward (R2) and no per-line tax column or allocation (R6); tax renders from `customer_bill_tax_item` as a bill-level summary. The template must state that the amount due covers current charges only.
